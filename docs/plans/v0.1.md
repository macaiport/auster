## A. The recipe format and the registry

### A1. What a recipe is

A recipe is a use, such as the household assistant, and the builds that can serve it. For people it is a
folder, `recipes/<label>/`, with a README and a findings file. For Auster it is an id in the registry.
Nothing on a Mac is found by the folder's name or the recipe's label. A label is changed by a later
`recipe` line (A3), never by editing one, so a rename needs no migration (T36).

**v0.1 serves one recipe per Mac** (BD14): the installer refuses a second recipe while one is installed.
The records are still kept per recipe, so that a later version can serve more.

### A2. Ids

Every recipe, build, engine and model has a minted id: one letter for the kind, then 12 characters of
lowercase base32 made from 60 random bits by `tools/mint-id` (macOS has no `base32` command; the tool
encodes it itself). Patterns: recipe `^r[a-z2-7]{12}$`, build `^b[a-z2-7]{12}$`, engine
`^e[a-z2-7]{12}$`, model `^m[a-z2-7]{12}$`, device key `^k[a-z2-7]{12}$`. An id is never reused. A
person types an id only in the pasted line (B2), which names the recipe.

### A3. The registry

`registry.tsv` at the root of the repo, read from the commit an install or update has fixed (B3 step 2,
D3.3). Plain text: one record a line, fields separated by single tabs, at most 1,000 bytes a line and
512 KiB in all. Lines starting `#` are comments. **No field is a URL or a path** (D4).

**The first line** is `auster-registry`, the format number and the version: `auster-registry	1	v0.1.0`.
A Mac reads only the format numbers it knows. Every v0.1 Mac knows format 1, and **format 1 is never
changed**: new information is added in new record kinds or in fields after the last, and **only ever adds
meaning; a restriction is only ever expressed by `withdraw`**. A registry of a format a Mac does not know
is not read at all, and every recipe shows `passed over (cannot be read)`. A later format, if one is ever
needed, is published beside `registry.tsv` under a new name; `registry.tsv` stays in format 1 for ever.

**Two families of record.** Facts never change: each id is defined once, and a released fact line is
never edited or removed. Judgements are appended: a later line about the same recipe replaces the
earlier one, and the earlier stays in the file.

| Record | Family | Fields, in order |
|---|---|---|
| `engine` | fact | id, platform, numbered build, file name, size, sha256, oldest macOS it runs on (major version, rounded up when the engine needs a point release: 14 for `b12359`, which needs 13.3) |
| `model` | fact | id, Hugging Face repository, commit, file name, size, sha256, licence, trust tier, context limit of the file |
| `build` | fact | id, engine id, model id, template sha256, system prompt sha256, test sha256, weights on the GPU (MiB), working buffers (MiB), the engine's memory outside the GPU (MiB), cache per token (bytes), temperature, top-p, the Mac it was measured on (a label) |
| `recipe` | judgement | recipe id, label, allowed trust tiers, people (default), context per person (minimum), context per person (maximum) |
| `order` | judgement | recipe id, then its build ids, preferred first: one to 64 of them |
| `withdraw` | fact | build id, reason |

| Field | Pattern |
|---|---|
| label, Mac label | `^[a-z][a-z0-9-]{1,40}$` |
| trust tiers | one or more of `publisher` (the model publisher's own file), `endorsed` (a third party's build linked from the publisher's own page), `third-party`, separated by commas |
| numbers | `^(0|[1-9][0-9]{0,8})$`, with ceilings: people 64, contexts 1,048,576, MiB 1,048,576, cache per token 4,194,304, oldest macOS 99. Read in base 10 always. No sum or product of them reaches 2^53 |
| size | `^(0|[1-9][0-9]{0,14})$` |
| platform | `macos-arm64` (the only one in v0.1) |
| numbered build | `^b[0-9]{4,7}$` |
| engine file name | `^llama-b[0-9]{4,7}-bin-macos-arm64\.(tar\.gz|zip)$` |
| repository | `^[A-Za-z0-9][A-Za-z0-9._-]{0,95}/[A-Za-z0-9][A-Za-z0-9._-]{0,95}$`: each part begins with a letter or digit, so that `..` cannot reach the download address a Mac builds from it |
| commit | `^[0-9a-f]{40}$` |
| model file name | `^[A-Za-z0-9][A-Za-z0-9._-]{0,200}\.gguf$` |
| sha256 | `^[0-9a-f]{64}$` |
| licence | `^[a-z0-9.-]{2,30}$` |
| temperature, top-p | `^(0(\.[0-9]{1,3})?|1(\.0{1,3})?)$` |
| reason | `^[a-z]{1,20}$`. Known: `security`, `egress`, `quality`, `licence`, `publisher`, `superseded`, `corrected`. An unknown one still withdraws, and shows as "withdrawn" |

- **Reading.** Records are read by JavaScript for Automation (BD17), which keeps empty fields. A line
  with fewer fields than its kind's is passed over, and so is a line with an empty field or one that fails
  any pattern. **Fields after the last one a Mac knows are kept, byte for byte, and not read** (T55): that
  is how format 1 grows (above). The repo's gate is stricter and requires each kind's exact count (T48),
  until a version that knows the new fields changes it. A record of an unknown kind is passed over. A line
  that names an id whose own line was passed over is passed over too. A file over 512 KiB is not read at
  all, and every recipe shows `passed over (cannot be read)`. The recipe a passed-over line belongs to
  says so (D3.3).
- **Order.** The latest `order` line for a recipe decides the order of its builds (D3.7). A build that is
  in no `order` line is never chosen.
- **Correcting a build.** A build's figures are facts. A wrong figure is corrected by a new `build`
  line with a new id and the same files, a new `order` line that puts it first, and a `withdraw` of the
  old one with the reason `corrected`, which shows calm words of its own and nothing alarming. Moving to
  it downloads nothing (D3.6 step 3).
- **Moving to a newer model or engine** is the same: a new `build`, a new `order`, and a `withdraw` with
  the reason `superseded` when the old build should no longer be offered.
- **Settled while building the reader (V2, 2026-11-26).** On a Mac, and by the gate:
  - a line is passed over when it has no final newline (a file cut short), holds any control character,
    is not UTF-8, or is empty;
  - a line may name an id defined further down the file;
  - a second `withdraw` of one build is passed over, and the first stands;
  - an `order` that names a build twice keeps its first place, and the gate fails it;
  - a build is named by one recipe's `order` lines only, since its test and system prompt are that
    recipe's; the gate fails a build named by two recipes;
  - the version on the first line is `v` and three base-10 numbers with no leading zeros;
  - a `recipe` line has at least one person, and its minimum context is at most its maximum; a Mac
    passes over one that has not, and the gate fails it;
  - a registry file that is a link is not read (D3.1);
  - `order` grows by new kinds, never by trailing fields, because its own length varies;
  - a recipe that serves a withdrawn build while another is waiting shows `waiting`, and `auster status`
    adds that the build it serves is withdrawn (D3.8);
  - a recipe line that narrows its tiers moves no Mac off a build it already serves; a restriction is
    expressed by `withdraw` (above).

### A4. Files Auster ships

`assets/` holds what a build needs besides the model: chat templates, system prompts and the recipe
tests. A file is named for people and found by its sha256. A template copied from llama.cpp, or taken
out of a model file, keeps its source and commit in the recipe's findings file, and is credited.
**Every build pins its template as a file in `assets/`,** even when the model file carries one, so that
the Jinja the engine runs on every request has been read by Auster.

### A5. The descriptor

What `builds/<recipe id>/serving` and each `kept` entry hold (D3.1): a first line `auster-descriptor 1`,
then the `build`, `engine` and `model` lines as they were in the registry, word for word, then the
**launch line**: people, context per person, port, the sha256 of the engine's unpacked file list (B3
step 9), and this Mac's own writing speed with this build at that setting (B3 step 13). Going back to a
kept build needs nothing else. The address is not in it: it is found at each start (B4).

**Writing speed**, wherever this plan uses it, is the rate the engine reports in its answer
(`timings.predicted_per_second`) to the **speed question**, shipped in the recipe's test file: "Count from
1 to 300, one number per line.", with `max_tokens` 128, at temperature 0, so that the rate is taken over
128 tokens as phase 1 measured it (36.9 tok/s for order 2 at four people × 32K, `docs/phase-1.md`, step
14). The launch line holds 0 for it from a switch until a server check measures it (B3 step 13) and
replaces `serving` by rename. The engine job does not read it, and the probe judges no `slow` while it is 0. **A speed of 0 means
the build has not passed a server check since the switch:** `auster status` says so (`auster restart` checks
it; when `kept` is not empty, `auster rollback` goes back), and the probe notifies `failed` or `down` at its first run while it is 0 (B5 step 6).

## B. The installer

### B1. Where things go

The data root is `~/Library/Application Support/Auster/`, mode 0700, owned by the person who installs,
with a marker file `.auster-data-root`. It holds `builds/` and `store/` (D3.1), `_update/`,
`engines/<sha256>/` (each engine build unpacked, with its file list), `keys/`, `logs/`, `bin/auster`, the
two jobs' programs (`jobs/auster-engine` and `jobs/auster-check`), `jobs/mint-id` for `bin/auster`, and
their previous versions. Outside it,
Auster writes only the two job files in `~/Library/LaunchAgents/` and, on a yes, one marked line at the
end of `~/.zprofile` (B6). The line in `CLAUDE.md` that names the data root is written before phase 2
creates it.

### B2. The way in

One line, pasted into Terminal:

```
/bin/bash -c "$(curl -q --proto '=https' --proto-redir '=https' --tlsv1.2 -fsSL https://raw.githubusercontent.com/macaiport/auster/refs/heads/release/install.sh)" auster-install <recipe id>
```

- `install.sh` is only a **bootstrap**: it is all functions and constants, and its last line calls
  `auster_install_main "$@"`, which with no arguments prints its usage and exits 2. A download cut short
  runs nothing. It fixes one commit and hands over to the driver in that commit's tree (B3 step 2), so
  every file that does the work comes from that one commit.
- `install.sh` never reads `~/.curlrc` and follows only HTTPS redirects, like every fetch Auster makes.
- To install a named version instead of the newest, `refs/heads/release` becomes `refs/tags/v<a>.<b>.<c>`
  in the same line; that install is `manual` (D3.2) and is never offered updates. It still reads the
  withdrawals in the registry `release` holds at that moment, and refuses a build withdrawn since (T96).
- `install.sh update` is the update (D3.6). `install.sh remove` removes an install that failed before
  `bin/auster` was written. `install.sh --check <recipe id>` runs every step in a temporary folder that it
  deletes, and changes nothing in the data root.
- Next to the line, the guide says that it fetches and runs the 17 MB engine to measure the Mac before it
  asks anything.

### B3. One procedure for installing and updating

**Installing is updating from nothing:** the same driver, the same steps, the same isolation and the same
order. The steps marked *first time* are skipped on an update. Every step is skipped when it is already
done, and "done" means equal, byte for byte, to what this commit's tree would write.

1. **Refuse what it must,** before writing anything: running as root; not Apple Silicon
   (`sysctl -n hw.optional.arm64`, which a Terminal under Rosetta does not hide); a macOS older than the
   floor (BD15), compared as a number on the major version.
2. **Fix one commit.** Ask GitHub's API for the commit `release` (or the tag) names now, fetch that
   commit's tree as one archive from `codeload.github.com/macaiport/auster/tar.gz/<commit>`, and check that
   the commit recorded inside the archive (its `pax` header's `comment=`) is the same. Run the driver from
   that tree.
3. **Take the lock and make the data root** (*first time*): `builds/updating` (D3.1); the data root with
   its marker; `bin/auster` and the jobs' programs, written by rename. From here on, `auster remove` works,
   whatever happens.
4. **Measure the Mac:** at a first install, fetch the engine named by the first build in this recipe's
   order (17 MB), check its size and sha256, unpack it as in step 9 into a temporary folder, and run
   `--list-devices`. On an update, the engine already in `engines/` is run instead, and nothing is fetched
   before the question (D3.6 step 1). The total it gives for `MTL0` is this Mac's GPU limit, kept in
   `builds/mac` with the memory, the macOS version and the date (C1); output without an `MTL0` line in
   the expected form refuses, and no limit is guessed. Read the sleep settings (`pmset -g`), whether the
   Mac has a battery and the firewall's state. The home network's router is recorded at a first install
   only; after that only `auster network` changes it (B4, BD9).
5. **Choose** (section C): the build, the number of people (the household's choice, carried over on every
   update), the context per person, and whether there is room on disk. A refusal says why, in this Mac's
   figures.
6. **The question.** What will be downloaded, how large, and, at a first install, roughly how long at the
   speed of step 4's fetch; how much memory it will hold; how many people at what context, and any change from what the
   Mac serves now; the address the household will use and the home network it is on, and that it is plain
   HTTP, which anyone on that Wi-Fi who sets out to can read; that the engine runs as this account, with
   its files; the sleep setting and whether Auster may keep the Mac awake (BD10); the firewall's state;
   and on a laptop, that always-on stops when the lid closes. A no removes whatever this run created and
   exits 1.

   **After a yes on an update that changes Auster's own programs** (`bin/auster` and the two jobs'
   programs), they change first, before anything is fetched for the model, while the engine serves as
   before (BD18). The programs in use are copied into `jobs/previous/`, unless that folder already
   exists (an earlier change never checked: nothing is copied over it); the new `bin/auster` answers
   `status` once from its temporary name, or nothing is renamed and the run ends with exit 3; the new ones
   are put in place by rename; the engine is restarted (`kickstart -k`) and the server check made (step
   13). Passed: the update goes on, `jobs/previous/` deleted. Otherwise the run stops with exit 4 and says
   that `auster rollback` puts the previous programs back with no download. Only the programs changed in
   that step, so a failure there is theirs. The check proves the engine job's program, the trial run
   proves `bin/auster`, and the check job's own program reports its first run in `auster status`. **An
   update that finds `jobs/previous/` already there** (a power cut after an earlier rename) restarts the
   engine and makes the check before anything is fetched, whether or not the programs change again.
7. **The model:** the publisher asked first (D3.6 step 1); fetched from the address that names its commit,
   resumable, stopped by `curl` if the speed falls below 10 KB/s for 120 s, with the Mac kept awake while it
   runs if the household said yes (`caffeinate -i -w`, BD10); size then sha256 checked with `openssl`; read-only in `store/`. Pasting the
   line again resumes it.
8. **The template, the system prompt and the test** from the tree, by sha256, into `store/`.
9. **The engine,** unpacked into a fresh folder of mode 0700: refuse any link that points outside it, any
   absolute or `..` name, any setuid bit. Write its file list (path, size, sha256 of each file) and record
   the list's sha256 in the launch line.
10. **The test, in isolation** (D3.6 step 4): the candidate on `127.0.0.1`, on a free port, with a key
    made for the test, with the engine's fitting off (`--fit off -ngl all`): at a first install and in
    turn at the household's setting (people × context), so that a build that does not fit fails here;
    on an update side by side, for one person at 8,192 (C5), while the old build keeps serving; a
    side-by-side test that fails is followed by a restart of the serving engine and a check (D3.6 step 5). The recipe's test (A7). On a fail:
    the build goes to `failed/`, and on a first install nothing is left loaded and the Mac is told what
    remains and how to remove it (exit 5).
11. **Keys** (*first time*): one per device, named by the household (B7), and Auster's own key for the
    probe. The key file the engine reads is written by rename and checked (B7).
12. **Switch** (D3.6 step 5): the old descriptor copied into `kept`, then `serving` replaced by rename,
    with a speed of 0 (A5). Then the jobs: written and loaded the first time, by `launchctl enable` and
    then `bootstrap`, as `auster start` does, so that a label left disabled by an earlier `auster stop` or
    `auster remove` loads; a `builds/stopped` left from before is deleted. On an update the engine then
    runs the new `serving` (D3.6 step 5).
13. **The server check.** One definition, used wherever this plan names it: from this Mac to its home
    address, within 180 s of this run's start of the engine, the speed question (A5) with a household key
    must be answered, and only after that answer a request with no key must be refused. A request with no
    key sent before the engine answers proves nothing: an engine still loading answers nobody. **Refused
    means HTTP 401 or 403 and nothing else:** the request with no key asks for one token, so that an open
    server answers it at once, and any other outcome (200, another code, a time-out, no answer) is
    `open`. The check fails closed, and so does the probe (B5). **It gives
    one of three results, and never exits;** only one result acts:
    - **passed:** the speed of that answer is written into `serving` by rename if the launch line holds
      0 (A5), and `jobs/previous/` is deleted if present;
    - **open,** the request with no key answered: the engine is stopped at once (`launchctl disable`,
      then `bootout`) and `builds/stopped` records the reason `open`;
    - **not answered:** nothing is done. The engine job's last start code is given if `start` is later
      than this run's start of the engine, and otherwise that the engine job has not run since. With
      fitting off, a build that does not fit at the household's setting answers every request with HTTP
      500 (B4; `docs/phase-1.md`, steps 11 and 14).

    The caller decides what follows. Here, passed goes on to step 14; open and not answered end the run
    with exit 4, saying so in plain words and naming the way back. After an update, a change of setting or
    a rollback, that is `auster rollback`, with no download. At a first install the jobs stay loaded, so
    that the engine job keeps trying; the keys are made but not shown and no stamp is written (`auster key
    show`, and pasting the line again); `auster remove` removes everything. **Nothing switches back by
    itself** (pass 2d, at the foot, says why; BD18), and the build is not put in `failed/`. **Any run of
    this procedure that finds `serving` with a speed of 0 or `jobs/previous/`, or that loaded the jobs, makes
    the server check before step 15,** so that a second run after a failure, which prints `OK` for the build, does not write
    the stamp over a server that is down.
14. **Show each new device's key** as a QR code (B7) (*first time*, and on `auster key add`).
15. **Record** the stamp (D3.1). Release the lock. Exit 0.

Exit codes: 0 done; 1 refused or answered no, and nothing of this run is left; 2 a usage error; 3 not
everything was updated (D3.6); 4 the server is down (D3.6), including when Auster stopped it because it answered with no key (step 13); 5 stopped after writing: what is left is
listed, and `auster remove` removes it.

**Settled while building the installer (V5, 2026-11-26).** `install.sh` is the bootstrap; it hands to
`common/driver.sh install|check <recipe id> --commit C --line release|tag --version V [--withdrawals FILE]`
(and `update`, `remove`), a contract that never changes once released (D3.9). `common/auster` is both the
`auster` command and the shell library the driver loads, so the lock, the data-root checks and the
server check exist once; step 3 copies it to `bin/auster`. The record forms written (lock, stamp,
`stopped`, `start`, the launch line, `failed/` names, the engine's file list) are given in
`common/auster`'s header, and U2's readers take them from there. Where B2 and B3 left a choice:

- **A tag install** knows its tag by `AUSTER_SELF_VERSION` in `install.sh`: when it differs from the
  version of `release`'s tree, the commit is fixed from `tags/<version>` and `release`'s registry is passed
  for its withdrawals. U9's gate checks that `AUSTER_SELF_VERSION` equals the tag.
- **Fixing the commit** asks `api.github.com/repos/macaiport/auster/commits/heads/<branch>` with
  `Accept: application/vnd.github.sha`, which answers the bare 40-character sha (checked live against
  `main` on 2026-11-26), then checks it against the archive's `pax` comment.
- **Step 1's refusals run in the bootstrap,** before anything is fetched; the driver refuses only root
  again. It also refuses a macOS below the engine line's oldest version.
- **`--check`** runs steps 3 to 5 in a temporary data root, prints the question without asking it, and
  exits 0: steps 7 to 15 would download and load jobs.
- **The `mac` record's keep-awake** is written right after the yes; **the first device's name** is asked
  with the question.
- **At a first install the publisher's `HEAD`** comes after the yes, in step 7's place; on an update, in
  D3.6 step 1's, before the question.
- **Exit codes:** before the yes every stop is exit 1 and removes what this run made; after it, every stop
  but the server check's is exit 5 and keeps partial downloads for a resume (step 8 included).
- **A first install's failed build** is retried by pasting the line again, without downloading again:
  `failed/` is not passed to the choice at a first install, and a pass removes its entry.
- **Step 4 measures with an intact engine already in `engines/`** rather than fetching it again.
- **`install.sh remove` fetches the tree** and runs the driver's remove; an offline removal before
  `bin/auster` exists is not built.
- **The firewall's state** is read with `socketfilterfw --getglobalstate`.

### B4. The engine job

`~/Library/LaunchAgents/local.auster.engine.plist`, written once and never changed: `Label`,
`ProgramArguments` = `/bin/bash` and `jobs/auster-engine` by absolute path, `KeepAlive` true,
`ProcessType` `Interactive`, `ThrottleInterval` 30, `StandardOutPath` and `StandardErrorPath` in `logs/`,
and `EnvironmentVariables` holding only `PATH=/usr/bin:/bin:/usr/sbin:/sbin`. All logic is in the program,
which is replaced by rename.

`jobs/auster-engine`:

1. **Waits** while `builds/paused` names a process of this boot that is alive (D3.1), at most 30 minutes.
2. **Reads `serving`** and matches every field, after the wait, so that it always starts what the last
   switch wrote.
3. **Checks the key file** (B7): a regular file, not a link, mode 0600, one to 64 lines, each a key and
   nothing else. Otherwise it writes `keys` into `start`, waits 60 s, and exits.
4. **Checks the engine and the template:** every file in the engine's list against its sha256 (42 MB
   unpacked, under a second), and the template against its sha256 in the `build` line. Otherwise `engine-hash`, wait 60 s, exit.
5. **Finds the home address.** The interface the default route uses must be a hardware port
   (`networksetup -listallhardwareports`), never a tunnel, its IPv4 address must be private (RFC 1918),
   and the router's hardware address (`arp -n <gateway>`) must be the one recorded at install or since by `auster network` (B6). Otherwise
   it writes `not-home` or `no-network`, waits 60 s, and exits: the engine listens nowhere but the home
   network.
6. **Writes `start`:** `starting`, the address, the boot session (`kern.bootsessionuuid`) and the time.
7. **Keeps the Mac awake** while the engine runs, if the household said yes (BD10): `caffeinate -i -w $$`.
8. **Execs the engine** with an empty environment (`env -i`, then the PATH above), its working folder
   `store/`, and a fixed set of options that no registry field can change: `-m` the model's sha256 as a
   relative name, `--alias` the build id (so that `/props` and `/v1/models` show no path or account name),
   `-c` people × context and `-np` people, `--host 127.0.0.1,<home address>`, `--port`, `--api-key-file`,
   `--offline`, `--no-slots`, `--no-webui-mcp-proxy`, `--cors-origins` its own two addresses (by number
   and by `.local` name), `--jinja` with `--chat-template-file`, `--ui-config-file`, `--temp` and `--top-p`
   from the build line, and the engine's default logging level. It never passes `--tools`, `--mcp-*`,
   `--media-path`, `--mmproj`, `--connect`, `--props` or `--slot-save-path`. The engine's own fitting
   is off when serving too (`--fit off -ngl all`), as in the test: section C decides what fits, and a
   setting that does not fit fails loudly, every request answered with HTTP 500 (`docs/phase-1.md`, steps
   11 and 14), rather than serving slowly with part of the model moved off the GPU.

The UI config is written by JavaScript for Automation (`JSON.stringify`) with exactly one key,
`systemMessage`, so that a system prompt with quotes cannot break it. Temperature and top-p reach the
engine as `--temp` and `--top-p` (step 8), and the chat page sends none of its own over them (D12).

The port is chosen at install by a connection test (`nc -z`): 8484 if nothing answers there, the next free
one if something does. It is kept in the launch line.

### B5. The check job

`~/Library/LaunchAgents/local.auster.check.plist`, written once: `RunAtLoad`, `StartCalendarInterval`
at seven minutes past every fourth hour (missed firings run on waking), `ProcessType` `Background`, no
`KeepAlive`. `jobs/auster-check`, each run, with a time limit on every part set by `curl --max-time` and a
watchdog of its own (`/usr/bin/timeout` is not assumed: it may not exist before macOS 26):

1. **The update check:** `updates.sh --refresh` (D3.3).
2. **The engine probe** (skipped while `builds/stopped` exists: the result is then `stopped`, never
   notified), on `127.0.0.1`, so that macOS's local-network permission never applies: the speed
   question (A5) with Auster's own key, one request with no key, and `/health`. Results in `_update/engine`: `ok` with its
   speed, `slow` (below half of this Mac's own baseline, A5; never while it is 0), `open` (the request with no key was
   answered), `broken` (`/health` 200 and the question HTTP 500, with a speed other than 0: an engine
   broken by memory, BD19), `failed` (any other error, or no answer within 120 s), or `down`. There is no `busy`: the engine
   gives no sign that its slots are full (`docs/phase-1.md`, step 13), so a probe that waited behind the
   household's questions once is not reported; only two failures in a row are (step 6).
3. **The address:** if the home address now differs from the one in `start`, it records that.
4. **Figures:** whether the served build still fits under section C with today's memory.
5. **Logs:** a log in `logs/` above 50 MB is truncated.
6. **A notification,** in fixed words (D3.5), **once for each change of state**, never on every run: an
   update waiting, a build withdrawn, `open` (at once), `broken` (at once, naming `auster restart`, BD19), `failed` or `down`
   twice in a row, or at once while the speed is 0 (A5), in a fixed sentence that names `auster rollback`
   when `kept` is not empty and `auster status` when it is, the address
   changed, a build that no longer fits.

**Nothing it does can stop, delay or restart the server** (D2.2): it reads and records, and its probe
waits in line like any request. T18 holds it to that.

**Settled while building the jobs (V6, 2026-11-26).** `common/auster-engine` and `common/auster-check`
give their record forms in their headers: `start`, `paused`, and `_update/engine` (seven keyed lines).
Where B4 and B5 left a choice:

- **The key file is checked strictly:** owned by this account, mode 0600, 1 to 64 lines of exactly 32 hex
  characters, each ending in a newline. `auster key add` and `key revoke` (V7) write exactly that, by
  rename.
- **The engine job also checks the system prompt's sha256,** since it writes the UI config from it. An
  unreadable `serving` stops it with `engine-hash`. A `paused` is over 30 minutes old by its file's time.
- **The probe is skipped while a live lock or `paused` exists,** so that a starting engine is not
  reported. An update and an install make their own server check (B3 step 13).
- **The probe judges the request with no key only when the engine is up** (`/health` 200, or the keyed
  question answered). `down` is a refused connection; a hung engine is `failed`. Only 401 or 403 is a
  refusal, as in the server check (B3 step 13).
- **Notifications:** a run of `failed` and `down` counts together, and `ok`, `slow` or `stopped` ends it.
  `open` names `auster restart`, which checks again and stops a server that is still open. A new address
  is told once, and cleared when the Mac is back on its address; a Mac off the home network is told
  nothing.
- **Fit with today's memory** (B5 step 4) is worked out from `serving`'s own three lines and its setting,
  so the check job never reads `_update/registry`. For this, step 3 copies section C's three JavaScript
  files into `jobs/` with the programs, and they count among Auster's own programs (B3 step 6).
- **The check job's update check** runs `_update/updates.sh --refresh` only if it is a regular file, under
  a 60 s watchdog, ignoring its exit code. When it is missing, the other parts still run. With no
  `_update`, or a data root not owned by this account alone, the check job does nothing.
- **Logs are truncated in place above 50,000,000 bytes.**

### B6. The `auster` command

`bin/auster`, a bash script. Subcommands: `status`, `update`, `rollback`, `unhold`, `cleanup`, `verify`,
`people <n>`, `key add <name>`, `key revoke <name>`, `key show <name>`, `stop`, `start`, `restart`,
`network`, `remove`. Every one that stops or starts the engine takes the lock. `stop` is `launchctl
disable` then `bootout`, so that it lasts across logins; `start` is `enable` then `bootstrap`, then it
deletes `builds/stopped` and makes the server check (B3 step 13), which writes it again if the server is
open; `restart` is `kickstart -k`, then the server check. **Every start of the engine by Auster is
followed by the server check,** so an open server is never left running. `builds/stopped` records why the
engine was stopped (`household` or `open`) for `auster status` to say; **while it exists, whatever its
reason and whether or not it can be read,** `update`, `people`, `restart`, `key add` and `key revoke`
refuse and name `auster start`, and `start`, `rollback`, `status`, `key show`, `verify`, `network` and
`remove` work. **`start`, `restart`, `key add`, `key revoke` and `rollback` exit 0 when the check passes
and 4 otherwise,** naming `auster start` after open and `auster status` after not answered; `key add` shows
the new key only after a passed check (`auster key show` gives it later). `network` records the current router as the home network. `people <n>` sets the number of
people, from 1 to the recipe's default, and runs the update's procedure for the build it serves only: the
tree is fetched for the recipe's limits, no other build is chosen, nothing is downloaded, no program is
changed and no stamp is written (C4, D3.6).

`status` also reports what macOS can switch off without Auster knowing: a job disabled in Login Items
(`launchctl print-disabled`), the sleep settings, and a `.local` name that macOS has changed.

The installer asks whether to add one line, marked as Auster's and quoted, to the end of `~/.zprofile`.
If `~/.zprofile` is a link, it is not rewritten: the line to add is printed instead.

### B7. Keys, devices and the QR code

- **One key for each device,** not each person: the chat page keeps its key in the device's browser, in
  plain text (`docs/phase-1.md`, step 3). Each is a minted id (`k…`, A2) with the household's name for
  the device beside it; a key is 32 hex characters from `openssl rand -hex 16`, in `keys/<id>`, mode
  0600, in a folder of mode 0700.
- **The engine's key file**, `keys/engine.keys`, holds every device's key and Auster's own probe key,
  which is never shown and cannot be revoked by `key revoke`. It is written to a temporary file and
  renamed, never in place.
- **Never an empty key file.** The engine treats an empty key file, or one of blank or comment lines, as
  "no key required" (`docs/phase-1.md`, step 12). The engine job refuses to start it (B4 step 3), and
  every check asks with no key and requires a refusal (B3 step 13, B5 step 2).
- **Getting a key onto a device:** a QR code of the key, drawn by JavaScript for Automation from macOS's
  own Core Image (BD17), on the terminal's alternate screen, written to the terminal only and never to a
  log, with the scrollback erased on leaving. The key reaches the drawing program on its input, never on
  a command line. Whether an iPad's camera reads a QR code drawn in Terminal is not yet tried (D12); if it
  does not, a window that Auster opens and closes itself is the fallback, never Preview (phase 1, step 7).
- `auster key add` and `auster key revoke` restart the engine, which reads its key file only at start
  (2.6 s with order 1 in memory, 1.3 s with order 2), and then make the server check (B3 step 13). An answer in progress on another device is cut.
- A QR code that signs a device in, rather than only giving it its key, waits for phase 6 (D11).

### B8. Removing Auster

`auster remove` takes the lock, stops the engine, boots out both jobs, deletes their files and `builds/stopped`, clears any
disabled mark launchd keeps for their two labels (`launchctl enable`), so that a later install can load
them, and removes the marked line from `~/.zprofile`. It then lists what is left in the data root, with sizes,
and deletes it only on a second yes, after checking that the path is the data root, holds the marker
file, and passes through no link. `install.sh remove` does the same for an install that failed before
`bin/auster` existed. Nothing else on the Mac was touched by Auster, apart from launchd's record that
the two labels are enabled, which it keeps (D12).

**Settled while building the keys and commands (V7, 2026-11-26).** `common/auster`'s header lists the
commands, the records and the test variables. Where B6 to B8 left a choice:

- **The last device's key is not revoked:** `key revoke` refuses it and names `auster key add`. The key
  file always holds a device's key beside Auster's own, and the server check, which asks with a device's
  key, always has one (T72 now says so).
- **A device's name** is a lower-case letter, then lower-case letters, digits and `-`, 40 at most. It is
  never part of a path: a device's files are found by reading every `keys/<id>.name`. A bad name exits
  2, a name already used exits 1. At most 63 devices, the engine's 64 lines less Auster's own key.
- **`key add`'s server check asks with the new key,** so a passed check shows that key works.
- **The `~/.zprofile` line is fixed:** `export PATH="$HOME/Library/Application Support/Auster/bin:$PATH"`,
  then the mark `# added by Auster; auster remove removes this line`. It names `$HOME`, not a real path.
  `remove` matches it byte for byte, so the line is a contract between versions: a version that changes it
  must remove both. It is asked right after the device's name and written at once on a yes; it is not
  asked when the line is already there, and no answer is no. `remove` deletes a `~/.zprofile` it leaves
  empty, so the home folder is as it was before the install. Two small differences remain: an empty
  `~/.zprofile` from before the install is deleted too, and a newline the installer added before its line,
  to a file that lacked a final one, stays.
- **The QR code is drawn on the terminal (`/dev/tty`),** never on standard output, which may be a log;
  the EXIT handlers of `bin/auster` and the driver erase it if a run is interrupted. T83 reads the drawn code back
  to the key with Core Image's own detector; whether an iPad's camera reads it from Terminal is still the
  owner's check (D12).
- **"Passes through no link"** is checked from the home folder down (`Library`, `Application Support`,
  the data root). macOS's own `/var` and `/tmp` are links, so the path above the home folder is not.
- **`bin/auster` mints ids with `jobs/mint-id`,** a copy of `tools/mint-id` made by the install (B3 step
  3), since the data root holds no `tools/`. It counts among Auster's own programs (B3 step 6).
- **`start` on a job already loaded uses `kickstart -k`,** so that the server check sees a start of this run.
- **`network` takes the lock,** since it writes `builds/mac`, and names `auster restart` rather than
  restarting.
- **Exit codes:** 1 for a refusal, 2 for a usage error, 3 for a command of a later step (`update`,
  `rollback`, `unhold`, `cleanup`, and `people`'s change of setting, each at its `TODO(U…)`), 4 for a
  failed server check.
- **`verify` is built** (AD13: every file `serving` names against its sha256); its test, T34, is U6's.

### B9. After a restart (AD15)

v0.1 uses launch agents, which run in the session of the person who installed. So after a restart the
server comes back **once that person has logged in.** With FileVault on, nobody can be logged in until
the disk is unlocked. A launch daemon would start without a login, but needs an administrator to install,
and whether the engine has the GPU as a daemon is not yet known (D12). The guide says plainly what a
restart means. AD15 stays open.

### B10. What is fetched, from where

From GitHub: the commit `release` names (its API), the tree of that commit (`codeload.github.com`), and
the engine archive from the llama.cpp project's release of the named build. From Hugging Face: the model
file, at the address that names the publisher's commit. Nothing else, and nothing large before the yes.

## C. The capability rules

### C1. The figures, from one place

| Figure | Where it comes from | Test variable |
|---|---|---|
| GPU limit (MiB) | the engine's `--list-devices`, the total for `MTL0` (53,084 MiB on the development Mac), measured at install and at every update and kept in `builds/mac` | `AU_GPU_MIB` |
| Memory (bytes) | `sysctl -n hw.memsize` | `AU_RAM_BYTES` |
| Free disk and volume size (bytes) | `df -k` on the data root's volume: physically free, not counting what macOS could clear | `AU_DISK_FREE_BYTES`, `AU_DISK_TOTAL_BYTES` |

A test variable is used only when it matches `^(0|[1-9][0-9]{0,14})$` whole. Every rule below takes its
figures from this one function and from the registry.

### C2. What a build needs

For a build serving P people at a context of N tokens each:

> on the GPU: weights + working buffers + cache per token × N × P
>
> in all: that, plus the engine's memory outside the GPU

Checked against phase 1's own reports: Magistral Small at 40K for one person, 13,302 + 272 + 6,400 =
19,974 MiB on the GPU (19.5 GiB), and for four at 32K each, 13,302 + 665 + 20,480 = 34,447 MiB; Mistral Small 4 for four people at 32K each, 41,923 + 333 + 2,880 =
45,136 MiB (44.1 GiB), the same as the engine's own projections (`docs/phase-1.md`, steps 13 and 14). The working
buffers grow with the total context, so a build line carries them at the recipe's largest setting (A6),
which overstates them at smaller ones.

### C3. Does it fit

A set of builds loaded at once fits when both hold:

1. **On the GPU:** the sum of their GPU needs, plus 1,024 MiB, is at most the GPU limit. 1,024 MiB is
   Auster's margin, the value the engine uses for its own fitting. It is needed: Mistral Small 4 with
   fitting off failed at a setting about 210 MiB inside the limit (`docs/phase-1.md`, step 14).
2. **For the rest of the Mac:** memory, minus the sum of their needs in all, is at least 12 GiB, so that
   macOS and the household's other apps keep room. 12 GiB is a first value, to be measured on the 36 GB
   MacBook (UL6).

On the development Mac: Mistral Small 4 for four people at 32K each needs 44.1 GiB on the GPU, leaving
7.8 GiB of the limit before the margin, and about 44.6 GiB in all, leaving about 19.4 GiB for the rest of
the Mac. Apertus at 48K would need 55.5 GiB on the GPU and does not fit.

### C4. Choosing the build and the context

The number of people is the household's choice, from 1 to the recipe's default, kept in the launch line and carried over on every update;
at first install it is the recipe's default, which the question lets the household lower. Then take the
recipe's builds in its latest `order` (A3), keep only the appropriate ones (D3.7), and for each take the
largest context per person, in steps of 1,024 from the recipe's minimum up to the smaller of its maximum
and the model file's own limit, that fits (C3). Use the first build that has one. If none has, refuse,
and say what this Mac has and what the smallest build needs.

An update that would change the context per person, or the build, says so in figures in its question.

The development Mac gets order 1 at 32,768 per person for four. A Mac whose GPU limit is about 27 GiB and
which has 36 GB of memory would get order 2: by arithmetic, 31,744 each for two people, or 15,360
each for four, the rule for the rest of the Mac binding in both. That is not measured;
UL6 measures it.

### C5. Side by side or in turn (D3.6 step 4)

On an update: side by side when everything already loaded, plus the candidate for one person at 8,192,
fits (C3); in turn otherwise. A first install has nothing loaded and nothing to go back to, and tests at
the household's setting (B3 step 10). Worked out at the question and again immediately before the test. The new build's
speed at the household's real setting is measured after the switch (B3 step 13), never during a
side-by-side test, when it shares the memory bandwidth with the build still serving. **An engine
cannot see another engine's memory**: a candidate beside a serving engine believed the whole GPU free,
and a pair over the limit by the sum broke both, the serving one until it was restarted
(`docs/phase-2.md`, section 6). Section C's sum is the only guard.

### C6. Room on disk (B3 step 5; D3.6 steps 1, 3 and 6)

There is room when free disk, less the download, is at least the larger of 20 GiB and 5% of the volume.
At first install, when the first build in the order fits in memory but not on disk, the question offers
the next one that does and says how much space the first would need (BD13). On an update, when there is
not room, the rule names the earlier builds whose removal would make it: failed builds first, then the
oldest kept, never the one in use, and the one before it only if the person says yes. A file in `store/`
or `engines/` counts only when no descriptor of any recipe names it.

**Settled while building section C (V3, 2026-11-26).** `common/capability-lib.js` holds the rules, and
its header gives every form, the `mac` record's among them (seven keyed lines after `auster-record 1`:
GPU limit, memory, macOS version, when measured, the router, and keep-awake; U2 writes it so). Where C1
to C6 left a choice:

- At a first install, with nothing loaded, the way is in turn; "one person at 8,192" is taken literally.
- A number of people carried over above a recipe default that has since been lowered is capped at the
  default, and the choice says the number used.
- The smallest build is the one with the least memory in all, at the household's people and the
  recipe's minimum context. A refusal says `fit` only when every build is ruled out by fit.
- The disk rule removes only this recipe's kept and failed builds, failed first and then the oldest
  kept; in that order it takes each build that frees space until there is room, and drops none it took:
  a failed build is never a rollback target, so removing it costs nothing. A build that frees nothing
  (its files shared with the build served, or with another recipe's) is never named, since removing a
  kept one would cost a rollback target for no room. "The one before the build in use" is the newest kept entry. Other recipes'
  descriptors only protect files.
- The unpacked engine (about 42 MB) and the files from the tree are not counted; the floor covers them.
  BD13's "space the first would need" is given both as the download and as the free space needed.
- A switch that fetches nothing (`auster people`) is given no disk figures.

### C7. What C does not do in v0.1

- **It does not predict speed.** Speed depends on the Mac's memory bandwidth. The recipe's test catches a
  build that does not fit by failing outright (A7), the check job compares each Mac with its own baseline
  (B5), and a rule that refuses a build for being slow waits for measurements on more Macs.
- **It does not weigh a model's quality.** The order is the recipe's judgement, made from measurements
  such as phase 1's quiz.
- **It does not keep more than one build loaded** for a recipe, and v0.1 serves one recipe (A1).

## D. The built-in update

### D1. What is true today (read and measured 2026-11-26)

**D1.1 The requirement.** The owner, 2026-11-26: the same update process as 1launcher, built in from
the start. Starting the model checks whether a newer Auster is out, and Auster can move to newer models
"as new ones become available/appropriate".

**D1.2 Where the mechanism comes from.** This is provenance: nothing from D2 on needs it, because the
rules are stated there in full. Auster's update began from 1launcher's. Read from `docs/plans/built-in-update.md` in that repo (shipped
as its `v0.3.1` on 2026-11-25). Section numbers below are that plan's.

- An installed Mac records which version each game was set up from, in a folder `_update` (3.1).
- At most once a day, when its window opens or a game starts, the Mac fetches one text file, the
  `CHANGELOG.md` on the branch `release`, and reads the newest version heading from it. A failure counts
  as that day's try. With no network nothing is said and the game starts (2, 3.2).
- The fetch is bounded at 1 MiB, the version is taken by one fixed pattern, and nothing fetched is run.
  Every value read back from `_update` is matched whole before use (3.1, 3.2, 3.8).
- "Newer" is decided by comparing version numbers, never by "different", because GitHub may answer
  with a copy up to five minutes old (3.2).
- When a newer version is out the window shows it with what changed. One click and a yes opens Terminal,
  which fetches the installer from `release` and runs it again for every game. **The installer is the
  update:** each step is skipped when already done (1.1, 3.4).
- Nothing installs without a yes (UD1). A file named `off` stops the check. A Mac set up from a
  checkout or a named version is never offered anything and never asks (2, 3.2).
- `release` moves only to a commit that a `v` tag names, and two GitHub rulesets stop `release` and the
  tags from being rewound or deleted (3.7, UD3, UD5).
- It was added after people had installed, so each existing install needed one more paste (UD9's answer, 11).

**D1.3 Measured here** (the Studio: `/usr/bin/curl` 8.7.1, bash 3.2.57, macOS 27.2.1).

gives curl exit 56 over HTTP/2 and 63 over HTTP/1.1, and keeps nothing. Without `-f`, a missing file
is exit 0 with the code `404`. With no route the code is `000`, and the exit is 6 when the name does
not resolve and 7 when nothing answers.

**D1.4 What is different here.**

1. **The server is always on.** 1launcher checks when something is opened. A household server starts at
   boot and may then run for weeks, with nobody at the Mac.
2. **Three things change, not one:** Auster's own scripts, the engine, and the model.
3. **A model is 14 to 44 GB.** A game update re-runs quick steps; this one downloads for minutes or hours.
4. **A worse model does not announce itself.** A game that will not start is obvious. A model that
   answers a little worse is not (concept, "Quiet failure modes").
5. **Changing the model may interrupt people.** Whether two builds can be loaded at once depends on
   the Mac and on the context length. A 14 GB file took 33.4 GB in all at a 128K context, so two do
   not fit in 55.7 GB at that context, and do at a smaller one.
6. **A build may need to be taken back,** for instance when a model is reported to misbehave (concept,
   "Trust tiers"). The channel that says "newer" can also say "withdrawn".
7. **Nothing is installed anywhere yet.** No Mac needs a second paste.

### D2. Target

1. An installed Mac knows what it runs: the version of Auster's scripts, once for the Mac, and for each
   recipe the build in use, with every file of that build by sha256.
2. At most one check a day asks GitHub what `release` holds: soon after the Mac starts, and then daily.
   With no network nothing is said. **The check can never stop, delay or restart the server.**
3. **One channel.** A new engine build or a new model reaches a Mac only as a new version of Auster
   whose registry names different files. There is no second place to watch.
4. When something is waiting, the person who looks after the Mac is told in fixed words that Auster
   ships, never in words fetched from the network. `auster status` says which recipes would change, how
   large the download is, and whether this Mac can run it.
5. Nothing is downloaded or installed without a yes, and nothing that runs unattended can give one.
6. A new build is put beside the one in use. It takes its place only after it has downloaded, matched
   its size and sha256, and passed the recipe's own test in isolation. If any of those fails, the Mac
   serves what it served before. Where the Mac has the memory, the test runs while the old build keeps
   answering, and the swap costs one restart of the engine. Where it has not, the server is down for the
   length of the test.
7. Going back is one command and needs no download, for as many earlier builds as that Mac's disk
   keeps. A build someone went back from is not put back by a later update.
8. A Mac set up from a checkout or a named version is never offered anything and never asks. It is also
   never told of a withdrawal; the guide says so.
9. A build can be withdrawn by a new line in the registry, and every Mac that checks is told within a day
   of the release that says so.
10. The check sends nothing about the household, sends the same requests whether or not anything is
    waiting, and one file switches it off.

### D3. Design

**D3.1 The records.** In the data root (B1). `builds/` and `store/` are what the server runs from.
`_update/` is only what the check knows, and `engines/` and `keys/` are described in B. **Every record
Auster writes carries its own format number,** so that an older version of Auster that meets a newer
record refuses and says how to remove, rather than misreading it. A descriptor's first line is
`auster-descriptor 1`. The first line of `mac`, `start`, `hold` and `_update/engine` is
`auster-record 1`. The one-line records (`scripts`, `offer`, `tried`, `noted`, `stopped`, `updating`,
`paused`) have `auster-record 1` as their first field. These carry none: `off`, which means something by
existing; what the engine reads (its key file, each `keys/` file and the UI config), whose form the
engine fixes; the engine's file list in `engines/`; the logs; the data root's marker; the fetched copies
(`registry`, which has its own format number (A3), `notes.md` and `updates.sh`); and what `store/` and
`engines/` hold, which is named by its sha256.

| In `builds/` | What |
|---|---|
| `<recipe id>/serving` | the build this recipe runs: a descriptor (A5) |
| `<recipe id>/kept/` | earlier descriptors still on disk, each a build at a setting, newest first, each file named by the date and the build id. A change of setting adds one; the entry gone back to leaves it; one with a speed of 0 is listed as never checked |
| `<recipe id>/failed/` | descriptors of builds that failed their test on this Mac, each file named by the date and the build id. Never served, never a rollback target, and not offered again until `auster update --retry` (D3.7) |
| `<recipe id>/hold` | the build ids this recipe is not to be moved to (D3.7), one to a line |
| `<recipe id>/start` | the engine job's last start: a code (`starting`, `keys`, `engine-hash`, `not-home`, `no-network`), the address, the boot session and the time. Read by `auster status` and the check job |
| `mac` | this Mac's figures for section C: GPU limit, memory, macOS version, the home network's router, and whether Auster may keep the Mac awake (B3 step 4) |
| `updating` | the lock on `builds/`: the process number, the boot session (`kern.bootsessionuuid`) and the process's start time. Taken by installing, updating, rollback, cleanup and every command that stops or starts the engine |
| `paused` | present while the engine must not run: the same three values for the process that asked (D3.6 step 4) |
| `stopped` | one line: why the engine was stopped, `household` (`auster stop`, B6) or `open` (B3 step 13), and when |

| In `store/` and `engines/` | What |
|---|---|
| `store/<sha256>` | model files, engine archives, templates, system prompts and tests. Read-only once verified |
| `engines/<sha256>/` | an engine archive unpacked (B3 step 9), with its file list |

| In `_update/` | What |
|---|---|
| `scripts` | the stamp, once for the Mac: the line followed (`release`, `checkout`, or `tag` for an install by a named version), the version of Auster's scripts, the commit, the time |
| `offer` | one line: the newest version `release` held at the last check that worked, and its time |
| `tried` | one line: the time of the last try, whether it worked or not |
| `notes.md` | the changelog as last fetched |
| `noted` | one line: the version last announced, and how often (1 or 2) |
| `off` | if it exists, nothing is ever fetched. Made by hand |
| `registry` | the registry as last fetched. Read only by `auster status`. Never the source of a size or sha256 for an install (D3.6) |
| `engine` | the check job's last probe (B5 step 2), the address it found, and the states already notified |
| `updates.sh` | the deployed copy of the rule file |

- **A process is alive** for `updating` and `paused` only when its number, its start time and the boot
  session all match. After a restart, process numbers start again, so a record from an earlier boot is
  treated as absent. A `paused` older than 30 minutes is treated as absent too.
- **A build has a minted id** (A2) that is never reused. Hold, kept, failed, withdrawn and rollback all
  name a build by it. A person sees a label and a date, and picks from a numbered list.
- **The recipe id is opaque too** (A1, A2): it appears in no path a person reads, and the folder name in
  the repo stays a label.
- **Files are counted by sha256 across recipes.** A file in `store/` or a folder in `engines/` is removed
  only when no `serving`, `kept` or `failed` descriptor of any recipe names it.
- **Ownership.** Before any write, the data root and every folder in it must belong to the person who
  installed, and nobody else may be able to write to them; the data root is mode 0700. Otherwise nothing
  is written. Both jobs run as that person, who is not root (AD15). Nothing in Auster runs as root.
- **Reading.** Every value read back is matched whole before use, a file that is a link is treated as
  absent (except that a `hold` then passes its recipe over and a `stopped` means stopped), and so is one
  too large once its format number has been checked, and nothing is ever run. The one-line records (`scripts`, `offer`, `tried`,
  `noted`, `stopped`) are read as a single line of at most 4,096 bytes of tab-separated fields. The first
  field of its first 4,096 bytes is checked first: `auster-record 1` is read on; a higher number makes Auster refuse, say how to
  update or remove, and leave the record as it is (T95); anything else makes the record absent. Only
  then are the fields counted, the format field among them: a second line, or a field too many or too
  few, makes the record absent. Descriptors, `hold`, `mac`, `start`, `_update/engine` and the registry
  get readers of their own, each with a stated bound and one pattern per field. `hold` is its
  format line, then one build id to a line, at most 64 lines. **A `hold` that cannot be read passes its recipe over; it is never
  treated as empty. A `stopped` that exists but cannot be read means stopped, reason unknown; it is
  never treated as absent.** The lock and `paused` are read by their own reader, never the generic one.
- **Moving `_update` to the Trash switches the update check off** for that Mac, because without the stamp
  the state is `none` (D3.2). Pasting the installer line again writes it again. `auster status` says so.

**D3.2 The rule file.** `common/updates.sh` holds the rules for what is installed and what is on offer.
Every caller uses it, and each install puts a copy in `_update`. It begins as a copy of 1launcher's file
at `b056bf3`, credited in its header, and is Auster's own from then on (AD12). Its rules:

- **The word for the Mac,** the first that applies: `off`, if the file `off` exists; `none`, if there is
  no stamp; `manual`, if the stamp's line is not `release`; `unknown`, if there is no `offer`; `ready`
  (D3.3); `current` otherwise. `manual` is for the whole Mac: a checkout is never offered anything.
- **Once a day.** `tried` holds the time of the last try. A try made less than a day after it fetches
  nothing. `tried` is written before the fetch, so a failure uses up the day (D3.4 has the one exception).
- **The bounded fetch.** `/usr/bin/curl` with the person's own curl settings ignored, HTTPS only, a
  ten-second limit and a cap of 1 MiB, the body to a file. The answer is taken only when curl's exit is
  0, the code is 200, the file is within the cap when measured again, and a version is found in it.
- **Newer, never different.** A version is three numbers compared as numbers, read from the first
  changelog heading of the form `## v<a>.<b>.<c> (`. An answer that names an older version than `offer`
  holds never lowers it, because an answer can be five minutes old.
- **The notes cleaner.** Before any fetched note is shown: headings lose their marks, paragraphs are
  joined, emphasis marks and every control character are removed, and the text stops at 200 lines or
  12,000 bytes with a pointer to the changelog.
- **A contract between versions on one Mac.** Its options and its output lines are used by callers built
  by other versions. A later version may add an option or a field at the end of a line, and never
  changes or removes one.
- **Its test variables:** the folder, a time that stands for now, and the two programs a test replaces
  (`AU_UPDATE_DIR`, `AU_UPDATE_NOW`, `AU_CURL`, `AU_OPEN`).

What Auster's file does that the one it began from does not: one stamp for the Mac in place of one per
game; the readers of D3.1; the second fetch, the joint write and the recipe lines of D3.3; the no-route
rule of D3.4; the ownership rule over `builds/` and `store/`; the call to section C's rule; and a
cleaner that also removes the two-byte control characters.

**Settled while building the rule file (U1, 2026-11-27).** `common/updates.sh`'s header gives its records,
its options and its output lines. Where D3.1 to D3.4 left a choice:

- **Names:** its functions are `auu_*`, apart from `common/auster`'s `au_*`.
- **The records it writes,** with times in seconds since 1970 so that "a day" is plain arithmetic:
  `offer` is `auster-record 1`, the version and the time; `tried` is `auster-record 1` and the time;
  `noted` is `auster-record 1`, the version and 1 or 2. The stamp keeps the installer's UTC time.
- **A record of a newer format** (D3.1): a newer stamp gives `none` with the detail `newer`, so the six
  words stay six; a newer `tried` or `offer` means nothing is fetched or written; a newer `noted` means
  nothing is printed.
- **The stamp's line** is matched as any lower-case word, and any word but `release` gives `manual`, the
  safe reading if a later version adds a line.
- **Each install deploys it at step 15,** by rename, just before the stamp and with mode 0644 as the jobs'
  programs, so that the stamp and the file that reads it are always of one version, and a run that stops
  with exit 4 or 5 changes neither. A first install whose server check fails leaves no `updates.sh`, which
  is harmless: with no stamp the word is `none`, and nothing is fetched. An update deploys it at the same
  point (U4).
- **The cleaner** takes the marks off every heading in a section shown, turns tabs into spaces so that
  words are not joined, removes the two-byte control characters (U+0080 to U+009F) but keeps the
  no-break space, and never doubles or ends on an empty line.
- **A version's three numbers** may have up to nine digits each, as the installer's pattern allows.
- **An `AU_CURL` that fails its pattern fetches nothing,** rather than falling back to `/usr/bin/curl`.
- **Callers read only the first line,** the state line. Each recipe's line (U3) comes from a new option,
  as the contract allows, never as more lines after the state line of an option that exists.
- **No extra headers:** the request is `curl -q --proto =https --tlsv1.2 -sS --max-time 10
  --max-filesize 1048576`, with the body to a file and the code from `-w`; what is sent is what curl
  sends by itself (D3.10, T14).

**D3.3 What a check fetches, and what it concludes.** Two small text files from `release`, **both on
every check**, each bounded at 1 MiB, each read by fixed patterns, neither run:

1. `CHANGELOG.md`: the newest version and what changed.
2. The registry (section A): every recipe's builds.

Fetching both every time means a second request never marks a Mac as behind.

- The registry's first line is its format number and its version. A Mac uses a registry only when that
  version equals the newest in the changelog just fetched: each file can be up to five minutes stale on
  its own (D1.3). `offer`, `notes.md` and `registry` are replaced together, and only when both files
  were read and their versions agree. Otherwise none of the three is written, the check counts as a
  failed try, and nothing is said.
- A registry whose format number the Mac does not know is not read (A3). Within a known format, a line
  of an unknown kind, a line with the wrong number of fields, and a line with any field that fails its
  pattern are passed over. A Mac that can use no build for a recipe shows that recipe as
  `passed over (cannot be read)` in `auster status` and sends no notification.
- The word for the whole Mac is one of the six of D3.2.
  `ready` means: the offered version is newer than the scripts version, **or some recipe has a build
  waiting.**
- Each recipe also gets one line: `same`; `waiting` (the build D3.7 picks for it is not the one it
  serves); `passed over`, with the reason (does not fit, no room, held, failed here, cannot be read); or
  `withdrawn` (a `withdraw` line names the build it serves).
- A person who says no to a build leaves it `waiting`. `auster status` keeps showing it and
  `auster update` offers it again. The notification is not repeated (D3.5).
- A notification is sent for a new version. A build that starts `waiting` for a reason on the Mac
  itself, such as memory freed, shows in `auster status` only.

**D3.4 When the check runs: two jobs, so that the check cannot hurt the server.**

- **The engine job** keeps the engine running. It starts what `serving` names and nothing else. It does
  not read `_update`, does not call `updates.sh` and fetches nothing. Before each start it checks the
  engine and the template against the sha256s `serving` gives (AD13). On a mismatch it does not start,
  and writes the reason into the recipe's `start` record. While `paused` names a process that is still
  alive, it waits.
- **The check job** runs `updates.sh --refresh` soon after it is loaded and then every few hours, and
  asks the engine one real question (B5). The
  rule file's `tried` stamp keeps that to one check a day. Every part has a time limit, set by `curl`
  and by a watchdog of the job's own (`/usr/bin/timeout` is not assumed), and its exit code is ignored.
  When `updates.sh` is missing, unreadable or failing, the check job does nothing. The probe goes to
  `127.0.0.1`, where the engine also listens, so macOS's local-network permission never applies.
- A try that never reached GitHub, because the Mac had no route yet, does not use up the day: the next
  firing tries again. "No route" means curl's exit code 6 or 7 on the first request. `tried` is written
  before the fetch, and put back to what it was only on those two codes. Every other
  failure uses up the day, a check stopped by its time limit included.
- **Why two.** launchd does not fire a timed trigger for a job it is already keeping alive (`man
  launchd.plist`). One job would therefore need a hand-written wrapper that supervises the engine and
  also sleeps for a day, and a fault in that wrapper or in the check would take the household's server
  down. Two plain jobs are fewer moving parts than that wrapper.
- A check that runs with nobody at the Mac is acceptable here because Auster is a background service
  already, and because the check can only read and record (T19).
- Whether the two jobs are launchd agents or daemons, and what that means on a Mac with FileVault, is
  decision AD15.

**D3.5 How the person is told.** v0.1 has no window. So:

- **A notification carries one fixed sentence that Auster ships.** It may include a version and a recipe
  label, each matched against its pattern first, and each passed to `osascript` as an argument, never
  built into AppleScript source. No text from the changelog or the registry is ever put in a
  notification. At most two per version, and otherwise once for each change of state (B5 step 6).
- **`auster status`** prints the word for the Mac, each recipe's line, what would change and how large
  the download is. It also says when checks are switched off and since when, which builds are held, and
  when a build in use is withdrawn, how the engine's last start went, and what macOS can switch off
  without Auster knowing (B6). Text from fetched notes
  appears only through the notes cleaner: control characters removed, length capped.
- A notification needs someone logged in at the Mac. If AD15 lands on a daemon there are none in v0.1,
  and `auster status` is the only channel.
- Either way, a Mac that nobody sits at tells nobody, and that includes a withdrawal. The gap is
  accepted for v0.1 and said in the guide. From phase 4 the launcher window and the menu bar fill it.

**D3.6 The update itself.** `auster update`, run at the Mac's own screen, writes a `.command` file and
hands it to Terminal, so that the person sees every line. The file is made in a new folder that only the
person can read, holds constants only, and removes itself and its folder when it ends. Run over SSH, the
update runs in that session instead, so the questions are asked where the person is. Either way it
fetches `install.sh` from `release` into a file, never into a pipe, and runs it only on a 200. **An update
is section B3's procedure on a Mac that already serves:** the bootstrap fixes one commit and runs the
driver from that commit's tree (B3 step 2), so every file that does the work comes from one commit, and
the code that drives an update is always the newest. The steps below are B3 steps 4 to 13 for a recipe
that is already installed: step 4 measures with the engine already in `engines/`, fetches nothing and
does not record the router again.

The driver holds the `updating` lock (D3.1). A second update, an install, a rollback, a cleanup, or a
command that stops or starts the engine, refuses while the lock is alive. A lock whose process is gone,
or that is from an earlier boot, is taken over.

**Every size and sha256 used below comes from the registry inside the fetched tree**, never from the
copy in `_update`.

For a recipe whose appropriate build is the one it serves, the steps print `OK` and nothing is fetched.
If only its setting changes (the number of people, or the context section C now allows), nothing is
fetched or tested: after the question it is a switch like any other, with the old descriptor copied into
`kept` and `serving` replaced by rename with the new launch line and a speed of 0, then the engine
restarted and the server check made (B3 step 13). Its way back is `auster rollback`, which lists the
earlier setting.
For one whose appropriate build is held, one line says so and nothing changes. For one with a different
build:

1. **Before anything is fetched.** The capability rule (section C) must say the new build fits, counting
   everything that would be loaded at the same time. The disk rule must say there is room: as things
   are, or after removing earlier builds it names. And, unless `store/` already holds the file, the
   publisher is asked about it with a `HEAD` request: a size or hash it reports that differs from the registry's stops the recipe, and so
   does a 404 ("the publisher no longer offers this file"). On any of these the recipe is passed over
   with one sentence, the other recipes go on, and the update ends with exit code 3 ("not everything was
   updated").
2. **The question.** What will change, including any change of build or of context per person, in
   figures (the household's number of people is carried over, C4); the download size; which earlier
   builds would be removed, and that they stay removed if the download then fails; which way the switch
   will go on this Mac, and for how long the server will not answer (side by side, a test that fails
   restarts the serving engine); and whether Auster's own programs
   change, which restarts the engine first (B3 step 6). Nothing has been fetched yet. A no leaves everything as it was
   and the build stays `waiting`.
3. **The download.** Skipped when `store/` already holds a file with that sha256. Otherwise the file is
   fetched from the address that names the publisher's commit, with no login and with the person's own
   curl settings ignored. A resume asks that same address again, never a saved address of the CDN, which
   expires. The size is compared, then the sha256. A mismatch deletes the download and stops this
   recipe. Room is worked out again before the download starts. Earlier builds are removed only at the
   moment the room is needed. The build before the one in use goes only if the question named it and
   the person said yes. A Mac whose disk cannot hold the build in use and the download together is
   passed over, with that reason.
4. **The test, in isolation.** The update itself starts the candidate, not the engine job: on
   `127.0.0.1` only, on a free port, with a key made for the test and deleted after it. No household key
   reaches it, and nothing on the network can. The recipe's test asks fixed questions and checks the
   form of the answers (A7). **A tool call is never run.** The candidate runs with the engine's fitting
   off (`--fit off -ngl all`), so that a build that does not fit fails here rather than serving slowly.
   Side by side it runs for one person at 8,192 (C5); in turn, at the household's setting.
   - **Side by side,** when section C says everything loaded plus the candidate fits with its margin:
     the engine job keeps serving during the test.
   - **In turn,** when it does not: the update writes `paused`, naming its own process (D3.1), and stops
     the engine (`launchctl kickstart -k`). launchd starts the engine job again, and the job waits for as
     long as that process is alive (B4 step 1). So an update that is killed, or a Mac that loses power,
     ends the wait by itself.

   Fit is worked out again immediately before the test. If the way has changed from what the question
   said, the recipe stops with exit code 3. It never changes way silently.
5. **The switch.** The candidate is stopped, whether it passed or failed. On a pass the old descriptor
   is copied into `kept` first, and then `serving` is replaced in one rename. On a fail the candidate's
   descriptor goes to `failed`, `serving` is untouched, and the recipe ends with exit 3. Then the engine
   runs again: in turn, by removing `paused`; side by side, by `launchctl kickstart -k`, so that launchd
   starts the job on `serving`, after a pass and after a fail alike, because a test that overflowed breaks
   the serving engine too. After a fail the check (B3 step 13) decides what is said: passed, the test's
   failure and exit 3; open, as B3 step 13 says; not answered, exit 4 naming `auster restart`, not
   `auster rollback`, since `serving` is the build it was. Then the update makes the server check and, on a failure, says and does
   what B3 step 13 says: exit 4, with `auster rollback` named. Nothing switches back by itself. When the
   check passes, its speed becomes this Mac's baseline for the build.
   - `serving` is rewritten only after a pass, and at every start the engine job serves what `serving`
     names. So a power cut at any point brings back the last build that passed its test: the old one if
     the cut came before the switch's rename, and otherwise the new one with a speed of 0, which `auster
     status` and the probe treat as not yet checked (A5).
   - A lock left by an update that died is reported by `auster status`. Unfinished downloads are
     counted by the disk rule and removed by `auster cleanup`.
   - Side by side, a test that overflowed the GPU breaks the serving engine as well, and it does not
     recover until it is restarted (`docs/phase-2.md`, section 6); hence the restart after a fail
     (step 5, T115).
   - **The takeover is a restart.** v0.1 has no front door, and `llama-server`'s router mode needs the
     model's name on every request, so one build cannot take over from another without a restart. The
     gap is the time the engine takes to start on files already tested: 2.4 to 2.9 s with them in memory,
     14.7 s for the 44 GB model from a cold disk (`docs/phase-1.md`, steps 4 and 10). A switch with no gap
     waits for phase 6's front door.
6. **Earlier builds stay on disk for as long as the disk rule allows.** Section C sets how much free
   space this Mac must keep. Above that, every earlier build stays. Below it, failed builds go first,
   then the oldest kept build, and never the one in use. `auster cleanup` lists what it would remove,
   asks, and removes nothing on a no.

`auster rollback <recipe>` goes back with no download. On either of its paths it starts the engine the
same way: `kickstart -k`, or `enable` and `bootstrap` while `builds/stopped` exists, which it then
deletes. **While `jobs/previous/` exists, it puts the previous programs back** by rename, deletes
`jobs/previous/` (the programs now in place are the ones last checked), starts the engine and makes the
server check, and changes no build. With nothing in `kept` and no `jobs/previous/`, it says so and exits 1.
Otherwise it lists `kept`, each entry a build at a setting, with any that are withdrawn or never checked
marked, and goes back to the one chosen **as a change of setting does**: it checks the size and sha256 of
that entry's engine, model and template again, copies `serving` into `kept`, renames the chosen entry
into `serving` with a speed of 0 (and out of `kept`), starts the engine, and makes the server check. **It runs
no test:** a kept build passed its test on this Mac before, its files are hashed again, and the server
check at the household's setting asks more of it than a test for one person. It refuses a failed build,
and a withdrawn one unless told `--withdrawn-ok`, when it prints why the build was withdrawn. **It never
writes `failed/`.** On a passed check it writes the build left behind into `hold` when that is a different
build; going back to the same build at an earlier setting holds nothing. Going back onto a build that is
itself held takes it off the list. On open or not answered it exits 4, as B3 step 13 says, and another
`auster rollback` can go further back. `auster unhold <recipe>` clears a
recipe's holds.

`auster verify` checks every file that `serving` names against its sha256 (AD13).

v0.1 keeps one build loaded for one recipe (A1, C7).

**D3.7 "Available and appropriate".** A build is available when the registry in the fetched tree lists
it. It is appropriate for a recipe on a Mac when the recipe allows its trust tier, the capability rule
says it fits, it is not withdrawn, it is not in that recipe's `hold`, and it has not failed its test on
this Mac (`failed/`; `auster update --retry` lets it be tried again). All five are decided on the Mac.
The installer never moves a recipe to a build that is not appropriate.

**Which build a recipe takes.** The latest `order` line for the recipe gives its builds an order (A3).
Of the appropriate ones, a recipe takes the first. `waiting` means that build is not the one it serves.
A build that comes after the one served is never offered, unless the one served is withdrawn or no longer
fits this Mac; it is otherwise reached only by `auster rollback`. Without this rule every Mac would be
`ready` for ever, since a released line is never removed (D3.8).

**D3.8 Withdrawn builds.**

- A build is withdrawn by a `withdraw` line in the registry that names it (A3), with a reason **code**.
  The known codes are `security`, `egress`, `quality`, `licence`, `publisher`, `superseded` and
  `corrected`; the words shown for each are Auster's own, from the code on the Mac. `superseded` and
  `corrected` have calm words and do not notify: they say a newer or corrected build is offered. A code
  that is not in the list still withdraws, and shows as "withdrawn" and nothing more. The `withdraw` record
  and its two fields are frozen for ever, so every Mac of every version can read every withdrawal.
- A build is withdrawn only by a release whose version rises. A registry line that has been released is
  never removed or changed; a withdrawal is a new line. The release gate holds both (D3.9).
- A Mac serving a withdrawn build says so at the next check, with a notification in fixed words, and in
  `auster status`, until it serves something else. It keeps serving. Auster never stops a household's
  server from a distance (AD9).
- A withdrawn build is never offered, and a rollback to one is refused without the flag (D3.6).
- A Mac whose state is `off` or `manual` is not told. The guide says so.
- The registry never loses a line and is not read above 1 MiB, so it has a ceiling. Section A caps a
  line at 1,000 bytes and the gate fails a registry over 512 KiB.

**D3.9 Releases and published names.** `release` moves only to a commit a `v` tag
names; the changelog's version headings have one fixed form, which a gate checks before a tag is made;
no tag is ever named `release`. Each change in the changelog opens with one bold sentence saying what a
household will notice. The gate here asks more questions:

- the registry's version line equals the tag, and its format number is 1;
- no fact line that `origin/release` holds is missing or changed, and no judgement line either (later
  judgements are added below, never edited in). With no `origin/release`, the gate fails unless it is
  told, by name, that this is the first release;
- no id is defined twice, every line has its kind's field count and passes every pattern, no line is over
  1,000 bytes and the file is at most 512 KiB (524,288 bytes);
- every `build`, `order` and `withdraw` names ids that are defined; every `order` names builds of its own
  recipe; every template, system prompt and test a build names is in `assets/` of the same commit with
  that sha256;
- every `model` and `engine` line that a non-withdrawn build uses answers a `HEAD` at its publisher with
  the registry's size and hash;
- when a build names an engine that no earlier released build used, the engine's `--help` is compared
  with the last released engine's, and every new or changed option is recorded in the recipe's findings
  file before the tag.

Before each move of `release`, the tagged commit is taken by `install.sh update` on one Mac, through the
test variables, **with that Mac's real figures, starting the engine through the new job programs and
each new build at the household's setting** (UL10). After each move, one installed Mac is looked at
within the day. The first release after
v0.1 changes no engine and no model, so the first real offer risks only the mechanism (AD14).

Once anyone has installed, these can never move: the address of `install.sh`, `CHANGELOG.md` and
`registry.tsv` on `release`; the form of the pasted line and of `install.sh`'s arguments
(`auster-install <recipe id>`, `update`, `remove`, `--check`); the contract between that bootstrap and
the driver in the tree; format 1 of the registry and the `withdraw` record; the form of every id; the list
of withdrawal reasons that have words (new ones may be added); the data root's path; the job labels
`local.auster.engine` and `local.auster.check` and their files; the marked line in `~/.zprofile`; exit
codes 1, 2, 3, 4 and 5; and the `start` codes. **Several of these carry the name Auster. The name's
checks (trademark search) are settled before `release` first moves,** or these keep the name whatever the
product is later called.

The repo has been public since 2026-11-26, and a file on `main` reads without a login. There is no
`release` branch yet, so the two files the check reads answer 404 until the first release. The tests
never use the network: they run against a stub curl that answers by address (the rule file's `AU_CURL`),
including `HEAD`, a range and the redirect.

**D3.10 Trust, and what this sends.**

- **What runs.** An update runs code from `release`. Whoever can move `release` reaches every installed
  Mac within a day, one yes away from running their code. It is the largest risk in this plan.
- **What stands against it.** The first yes: the one given before the fetched installer runs. The
  questions asked later are asked by the fetched code itself, so they do not protect against a bad
  release. The rulesets stop `release` being rewound or deleted and a `v` tag being moved. They do not
  stop `release` being moved forward to any commit, or a new tag being made: "only tagged commits" is the
  owner's own gate, which an intruder skips. None of this stops whoever holds an owner's credential: the
  owner, any session on the owner's Macs that can push, a token GitHub holds for the repo, or GitHub
  itself.
- **Model and engine files are not trusted by where they come from.** Each is named in the registry by
  size and sha256. Hugging Face and its CDN carry the bytes and cannot change what a Mac accepts. GitHub
  can: it serves the registry those hashes come from.
- **A hash shows that a file is the one that was chosen, not that it is safe.** Safety rests on the
  short list of models, the trust tiers, the templates Auster pins and reads (A4), and the options it
  never passes (B4 step 8).
- **Isolation is only for the test.** During its test a candidate is cut off from the network (D3.6 step
  4). In service the engine runs as the household's account, with that account's files, and no sandbox
  (BD16). A flaw in the engine that any key can reach reaches that account. Phase 2 tries `sandbox-exec`.
- **Plain HTTP on the home network** (B3 step 6). Anyone on the Wi-Fi who sets out to can read a device's
  key, and a device on the network that answers for the Mac's `.local` name can serve its own page and
  read a browser's saved key and conversations. HTTPS needs a certificate the household's devices trust:
  a later phase.
- **What is sent.** Two requests to GitHub on each check, the same two whether or not anything is
  waiting, and at install or update one more to learn the commit `release` names. Each names curl and its version, and nothing of Auster's. GitHub sees the Mac's network
  address and the time, which is shortly after the Mac starts or one of the check job's daily times. A
  download is seen by Hugging Face and by the CDN it redirects to: the address, the file and the time,
  with no login.
- **Who is never asked.** A Mac whose state is `off`, `none` or `manual`.

### D4. What section D needs from A, B and C

Sections A to C answer each item below. What they leave open is in D12.

- **From A:**
  - The form of a recipe id and of a build id, each as a pattern. Both minted, neither reused.
  - The registry: its first line (format number, version), and the form of a build's line. No field is a
    URL or a path. Each field has a pattern, and addresses are built from fixed hosts and matched fields:
    the model's repository, commit and file name; the engine's numbered build and file name; sizes;
    sha256s. An engine build is named by its build number and file name, never by a version such as
    "1.0.0", and never by a name worked out from a pattern (D1.3).
  - What the capability rule needs to know about a build: its size, its context length, and what it
    costs in memory per person.
  - A label for people, with its pattern; the trust tier; the withdrawn mark and its reason code.
  - The recipe's test: how it is run, its time limit, what counts as a pass, and that it gives the same
    result twice.
- **From B:**
  - The data root. Where `auster` lives and how it reaches the person's `PATH`.
  - An installer whose every step is skipped when already done, so that running it again is the update;
    that honours `hold`; and that asks the question of D3.6 step 2 itself. `install.sh update`, and the
    driver for every recipe set up on the Mac. A dry run.
  - Exit codes: 0, 3 (not everything was updated) and 4 (the server is down) are fixed here; B fixes the
    rest, and the sentences a person reads.
  - The two launchd jobs, their user, and decision AD15.
- **From C:** rules evaluated on the Mac, never constants. Does this set of builds fit together, loaded
  at once, at the working context and with people using it. How much disk must stay free on this Mac,
  and which earlier builds may be removed to make room. Each answers with a reason a person can read.
  Each takes its figures for memory and disk from one place, which a test can replace.

### D10. Rollback

- **Before `release` first moves:** nothing has reached anyone. Revert on `main`.
- **A wrong release:** it gets a successor, and installed Macs are offered it within a day. `auster
  update` always fetches the newest installer, so a release whose installer is wrong is repaired by the
  next one.
- **What a successor cannot repair:** the deployed `updates.sh`, the check job's program and the writer
  of the `.command` file. A release that breaks one of those leaves the Macs that took it silent, repaired only
  by one paste of the installer line. That is this plan's blast radius. It is why the check cannot
  affect the server (D3.4, T18), and why each release is run on one Mac before `release` moves and
  looked at after (D3.9).
- **A broken engine job program:** an update that changes it does so in a step of its own, straight
  after the question, on the build already serving, and makes the server check; on a fail it stops and
  names `auster rollback`, which puts the previous programs back with no download (B3 step 6, BD18,
  T94). A fault that shows
  only at a later start is the blast radius here: the pre-move run starts the engine through every new
  program on a real Mac before `release` moves (UL10).
- **A wrong model:** `auster rollback` on the Mac, which holds it there; and a successor release that
  withdraws the build.
- **A wrong figure in a build line:** a corrected build of the same files, ordered first, and a
  `withdraw` of the old one with the reason `corrected` (A3). Moving to it downloads nothing.
- **Going back to an older Auster:** by pasting the installer line with a tag (B2). The state becomes
  `manual` and nothing is offered until the plain line is pasted again. An older version refuses records
  with a newer format number and says how to remove (T95); it never rewrites them.
- **An install that failed partway:** `auster remove`, or `install.sh remove` if it failed before
  `bin/auster` was written (B8).
- **The check alone:** the file `off`.
- **The check's records:** `_update` holds nothing the server uses. Moving it to the Trash switches the
  update check off until the installer line is pasted again (D3.1). `builds/` is not like that: it is
  what the server runs from.

### D11. Not in this plan

- Silent updates of any kind.
- Signing of what is fetched. The sha256 in the registry is the check. Requiring signed tags on
  `release` is worth its own look.
- A window, a menu-bar item, a progress bar: phase 4.
- A switch with no gap, a household's own switch to stop on a withdrawal, and a QR that signs a device
  in rather than only giving it its key (`docs/phase-1.md`, step 7): all wait for phase 6's front door.
- Staging. Every Mac is offered the same version within a day. Exposure is limited by the yes, by AD14,
  and by how fast a release is replaced or a build withdrawn.
- Any report from a Mac to the maintainer. A model that answers worse is learned of only from an issue
  someone chooses to open; `auster rollback` prints where.
- The Apertus output filter for personal data. Its publisher has not released one yet.
- A mirror for a model whose publisher removes the file. A removed file means the recipe is passed over
  with a sentence, and a successor release names another build. Earlier builds kept on disk are the
  only copy a Mac has.
- MLX builds, Windows and Linux.
- More than one recipe on a Mac (BD14), and more than one build loaded at once.
- HTTPS on the home network, a sandbox for the engine, and a separate account for it (BD16, AD15).
- A rule that refuses a build for being too slow on a Mac (C7).
