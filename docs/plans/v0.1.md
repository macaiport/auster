## D. The built-in update

### D1. What is true today (read and measured 2026-11-26)

**D1.1 The requirement.** The owner, 2026-11-26: the same update process as 1launcher, built in from
the start. Starting the model checks whether a newer Auster is out, and Auster can move to newer models
"as new ones become available/appropriate".

**D1.2 What 1launcher's update does.** Read from `docs/plans/built-in-update.md` in that repo (shipped
as its `v0.3.1` on 2026-11-25). Section numbers below are that plan's.

- An installed Mac records which version each game was set up from, in a folder `_update` (3.1).
- At most once a day, when its window opens or a game starts, the Mac fetches one text file, the
  `CHANGELOG.md` on the branch `release`, and reads the newest version heading from it. A failure counts
  as that day's try. With no network nothing is said and the game starts (2, 3.2).
- The fetch is bounded at 1 MiB, the version is taken by one fixed pattern, and nothing fetched is run.
  Every value read back from `_update` is matched whole before use (3.1, 3.2, 3.8).
- "Newer" is decided by comparing version numbers, never by "different", because GitHub may answer
  with a copy up to five minutes old (3.2).
- When a newer version is out the window shows it with what changed. One click and a yes opens Terminal,
  which fetches the installer from `release` and runs it again for every game. **The installer is the
  update:** each step is skipped when already done (1.1, 3.4).
- Nothing installs without a yes (UD1). A file named `off` stops the check. A Mac set up from a
  checkout or a named version is never offered anything and never asks (2, 3.2).
- `release` moves only to a commit that a `v` tag names, and two GitHub rulesets stop `release` and the
  tags from being rewound or deleted (3.7, UD3, UD5).
- It was added after people had installed, so each existing install needed one more paste (UD9, 11).

**D1.3 Measured here** (the Studio: `/usr/bin/curl` 8.7.1, bash 3.2.57, macOS 27.2.1).

| Asked | Answer |
|---|---|
| Hugging Face API for `mistralai/Magistral-Small-2509-GGUF` | Not gated. Commit `429b90d8a8f0037241db6fab46a20b0f90859b03`. `Magistral-Small-2509-Q4_K_M.gguf` is 14,334,432,256 bytes, sha256 `d3a024d2…a43434`. The API gives a sha256 for every large file. |
| `HEAD` on that file at `.../resolve/<commit>/<file>`, no login | 302 to a CDN. Headers: `x-linked-size: 14334432256`, `x-linked-etag` equal to the sha256, `x-repo-commit` equal to the commit, `accept-ranges: bytes`. So a file can be named by commit, checked before download, and resumed. |
| GitHub release `v1.0.0` of `ggml-org/llama.cpp` | **One file, `nightly-tag.txt`. No programs.** The macOS programs are attached to the numbered builds (`b12756` and its neighbours, several a day) as `llama-b<n>-bin-macos-arm64.tar.gz`, and the API gives each a sha256. |
| Homebrew's `llama.cpp` 1.0.0 | Built from the tag `v1.0.0`. The arm64 bottle has its own sha256. |
| `raw.githubusercontent.com/macaiport/auster/...` with no login | **404.** The repo is private. |
| sha256 of a 14.3 GB file on the Studio | Ran to the end in the background. **Not timed.** Phase 1 times it (it bears on AD13). |

Taken from 1launcher's plan (1.5) and not measured again: `raw.githubusercontent.com` answers with
`cache-control: max-age=300`; `--max-filesize` gives curl exit 56 or 63 and keeps nothing; without
`-f`, a missing file is exit 0 with the code `404`.

**D1.4 What is different here.**

1. **The server is always on.** 1launcher checks when something is opened. A household server starts at
   boot and may then run for weeks, with nobody at the Mac.
2. **Three things change, not one:** Auster's own scripts, the engine, and the model.
3. **A model is 14 to 44 GB.** A game update re-runs quick steps; this one downloads for minutes or hours.
4. **A worse model does not announce itself.** A game that will not start is obvious. A model that
   answers a little worse is not (concept, "Quiet failure modes").
5. **Changing the model may interrupt people.** Whether two builds can be loaded at once depends on
   the Mac: two 14 GB builds fit in 64 GB, two 44 GB builds do not.
6. **A build may need to be taken back.** The owner removed a model from this Mac on 2026-10-26 after a
   report that it tried to send data out. The channel that says "newer" can also say "withdrawn".
7. **Nothing is installed anywhere yet.** No Mac needs a second paste.

### D2. Target

1. An installed Mac knows what it was set up from: the version of Auster, and for each recipe the engine
   build and the model file in use, each by sha256.
2. At most once a day the Mac asks GitHub which version `release` holds: when the server starts, and
   then daily while it runs. With no network nothing is said and the server is not delayed.
3. **One channel.** A new engine build or a new model reaches a Mac only as a new version of Auster
   whose recipe names different files. There is no second place to watch.
4. When a newer version is out, the person who looks after the Mac is told what changed in plain words.
   If it changes a model on this Mac, they are told which, how large the download is, and whether this
   Mac can run it.
5. Nothing is downloaded or installed without a yes.
6. A new model or engine is put beside the one in use. It replaces it only after it has downloaded,
   matched its size and sha256, and passed the recipe's own test. If any of those fails, the Mac serves
   what it served before. Where the Mac has the memory, the new build is tested while the old one keeps
   answering and nobody is interrupted. Where it has not, the swap costs a short outage.
7. Going back is one command and needs no download, for as many earlier builds as that Mac's disk has
   room to keep.
8. A Mac set up from a checkout or a named version is never offered anything and never asks.
9. A build can be marked withdrawn, and every Mac that runs it is told within a day.
10. The check sends nothing about the household, and one file switches it off.

### D3. Design

**D3.1 The record.** A folder `_update` in Auster's data root, as in 1launcher. Where the data root is
belongs to section B; it is a new place outside the repo and gets its line in `CLAUDE.md` first.

| File in `_update/` | What |
|---|---|
| `installed/<recipe id>` | the stamp: the line the recipe follows (`release` or `checkout`), the version, the commit, the time |
| `serving/<recipe id>` | what the recipe runs now: engine build and its sha256, model file and its sha256, template sha256 |
| `kept/<recipe id>/` | the same, one entry for each earlier build still on disk, newest first. How many there are is the disk rule's answer on that Mac (D3.6) |
| `hold/<recipe id>` | a version this recipe is not to be offered again (D3.7) |
| `offer`, `tried`, `notes.md`, `noted`, `off`, `updating` | as in 1launcher's 3.1 |
| `registry` | the registry as last fetched (D3.3) |
| `updates.sh` | the deployed copy of the rule file |

- **The key is the recipe id, and it must be opaque.** 1launcher keys on the Steam app ID, which someone
  else minted and which never changes. Auster has no such number. `household-assistant` is a label and
  will be renamed one day. Section A therefore gives each recipe a minted id that appears in no path a
  person reads, and the folder name stays a label (`shared.md`, keys are opaque).
- Every value read from `_update` is matched whole before use, a file that is a link or too large is
  treated as absent, and nothing there is ever run. These rules are 1launcher's 3.1, taken as they are.

**D3.2 The rule file.** `common/updates.sh`, copied from 1launcher at `b056bf3`, which stays the
original: a fault found here is fixed there first and copied again. Its states (`off`, `none`,
`manual`, `unknown`, `ready`, `current`), its once-a-day rule that counts failures, its bounded fetch
and its "newer, never different" comparison carry over unchanged. What changes: the names, the
address, the key (recipe id for Steam app ID), and the additions below. Its options and output lines
are a contract between versions on one Mac, as there.

**D3.3 What a Mac fetches.** Two small text files from `release`, both bounded at 1 MiB, both read by
fixed patterns, neither run:

1. `CHANGELOG.md`, daily at most: the newest version and what changed.
2. The registry, only when the first fetch showed a newer version. It lists every recipe's builds
   (D4). With it the Mac works out, by itself, which of its recipes would change, how large the
   download is, and whether the new build fits. Nothing about the Mac is sent to find this out.

**D3.4 When the check runs.** At server start, in the background, never waited for. And once a day
while the server runs, from the same launchd job that starts the engine: its script wakes daily and
calls `updates.sh --refresh`. There is no second job (fewest parts). The rule file's own `tried` stamp
is what keeps it to one request a day, however often it is called. This is the one place the design
leaves 1launcher, which runs nothing when no app is open (its section 11). Auster is a background
service already.

**D3.5 How the person is told.** v0.1 has no window. So:

- a macOS notification, at most twice per version, as 1launcher's launchers do (UD6);
- `auster status`, which prints the state line and, when an update waits, what it would change;
- from phase 4, the launcher window and the menu bar.

A Mac that nobody sits at shows its notification to nobody. `auster status` over SSH is the way there
until phase 4. That gap is accepted for v0.1 and said in the guide.

**D3.6 The update itself.** `auster update` writes a `.command` file and hands it to Terminal, as
1launcher's 3.4 does, so the person sees every line. It fetches `install.sh` from `release` and runs
`install.sh update`, which runs the installer of every recipe set up on the Mac. The code that drives
an update is therefore always the newest.

For a recipe whose build did not change, the installer's steps print `OK` and nothing is downloaded.
For one whose build changed:

1. **Before anything is fetched:** the capability rule (section C) must say the new build fits this
   Mac. The disk rule must say there is room: either as things are, or after removing earlier builds
   it names, which happens only after the yes. If neither, the recipe is passed over with one sentence
   saying why, the other recipes go on, and the update ends with exit code 3 ("not everything was
   updated").
2. **The question.** What will change, the download size, which earlier builds would be removed, and
   whether the swap will interrupt the server on this Mac (step 4). Nothing so far has been fetched.
   A no leaves everything as it was.
3. **The download,** beside the file in use, from an address that names the publisher's commit. It is
   resumable. Its size is compared, then its sha256, against the registry's. A mismatch deletes the
   download and stops this recipe.
4. **The switch,** in one of two ways. Section C's rule picks the way on each Mac; the plan does not.
   - **Side by side,** when memory holds both builds at the recipe's working context with the rule's
     margin. The new build is loaded beside the old one and tested while the old one keeps answering.
     On a pass it takes over. On a fail it is unloaded and nothing else has changed.
   - **In turn,** when it does not. The server stops, starts on the new files, and is tested. On a
     fail the server starts again on the old files.

   Either way the test is the recipe's own: fixed questions with checks on the answers' form,
   including a tool call. On a pass, `serving` and `kept` are rewritten. A build that failed is kept
   for inspection, named as failed.
5. **Earlier builds stay on disk for as long as the disk rule allows.** Section C sets how much free
   space this Mac must keep. Above that, every earlier build stays. Below it, the oldest goes first,
   and never the one in use. `auster cleanup` removes them on request.

`auster rollback <recipe> [<build>]` goes back to the build before, or to any build still kept. It
switches by the same two ways, runs the test, and writes `hold` with the version left behind.

Where a Mac has room to keep several models loaded at once, which ones it keeps loaded is also a rule
of section C, not of the update.

**D3.7 "Available and appropriate".** A build is available when the registry on `release` lists it. It
is appropriate for a Mac when the recipe allows its trust tier, the capability rule says it fits, and
it is not withdrawn. All three are decided on the Mac. A recipe that holds a version is not offered
that version again; it is offered the next one.

**D3.8 Withdrawn builds.** A registry line can mark a build withdrawn, with a reason. A Mac serving that
build says so at the next check, at every start, and in `auster status`, until it serves something
else. It keeps serving. Auster never stops a household's server from a distance (decision AD9).

**D3.9 Releases and published names.** As 1launcher's 3.7: `release` moves only to a commit a `v` tag
names; the changelog's version headings have one fixed form, which a gate checks before a tag is made;
no tag is ever named `release`. Each change in the changelog opens with one bold sentence saying what a
household will notice. Once anyone has installed, these can never move: the address of `CHANGELOG.md`
and of the registry on `release`, the word `update` after `install.sh`, and the form of a registry line.

**The check cannot work while the repo is private** (D1.3: 404). Until the repo is public the whole
process is built and tested against a local file server, through the test variables the rule file
already has.

**D3.10 Trust, and what this sends.**

- **What runs.** An update runs code from `release`. Whoever can move `release` reaches every installed
  Mac within a day, in words they choose, one yes away from running their code. That is 1launcher's 3.8,
  and it is the largest risk in this plan.
- **What stands against it.** The yes. The rulesets on `release` and on the `v` tags. `release` moving
  only on the owner's word. None of these stops someone who holds an owner's credential.
- **Model and engine files are not trusted by where they come from.** Each is named in the registry by
  size and sha256, and the registry comes from `release`. Hugging Face and GitHub carry the bytes; they
  cannot change what a Mac accepts.
- **What is sent.** One request a day to GitHub, and a second on a day when a newer version appears.
  Neither names the Mac, the version installed, or the recipes. A download tells Hugging Face the Mac's
  network address and which file it fetched, with no login.
- **Who is never asked.** A Mac whose state is `off`, `none` or `manual`.

### D4. What section D needs from A, B and C

- **From A:** an opaque recipe id. A registry a shell can read line by line with fixed patterns. For
  each build: engine (where from, which build, size, sha256); model (repository, commit, file, size,
  sha256); chat-template sha256; sampling settings; trust tier; a withdrawn mark with a reason.
- **From B:** an installer whose every step is skipped when already done, so that running it again is
  the update. `install.sh update`. A dry run. The data root. **Where the engine program comes from:**
  D1.3 shows the stable tag publishes none, so it is a numbered build's file or Homebrew's bottle.
- **From C:** rules evaluated on the Mac, never constants. Does this build fit. Do these builds fit
  together, for a side-by-side test or to stay loaded. How much disk must stay free on this Mac, and
  which earlier builds may be removed to make room. Each answers with a reason a person can read.

### D6. Tests

Each runs against a local file server and stub programs, with no network. Each mutant is applied to the
real source, seen to turn its test red, and removed.

| | Test | Mutant that must turn it red |
|---|---|---|
| T1 | A newer version on offer gives the state `ready`; the same or an older one gives `current` | compare versions as text, so `v0.10.0` reads as older than `v0.9.0` |
| T2 | With the server unreachable, the start finishes in its usual time and nothing is said | wait for the fetch before starting the engine |
| T3 | An answer over 1 MiB is dropped and the offer is unchanged | remove the size check after the fetch |
| T4 | Two checks in one day make one request; a failed check also uses up the day | write `tried` only after a fetch that worked |
| T5 | With `off` present, or a stamp on `checkout`, no request is made | test `off` after the fetch |
| T6 | A value in `_update` with a second line, or with `$(...)` in it, is treated as absent | read the file with one `read` and no second read |
| T7 | A no at the question leaves no new file on disk and the server untouched | start the download before the question |
| T8 | A download whose sha256 differs is deleted and the server still answers on the old model | compare the size only |
| T9 | A new build that fails the recipe's test, by either way of switching: the server answers on the old model, and `serving` is unchanged | rewrite `serving` before the test |
| T10 | Too little disk even after removing the earlier builds the rule allows: the recipe is passed over before any fetch, others go on, exit code 3 | check the disk after the download starts |
| T11 | A build the capability rule rejects is never offered for that Mac | offer every build the registry lists |
| T12 | After `auster rollback`, the same version is not offered; the next one is | do not write `hold` |
| T13 | A withdrawn build is named at every start until changed, and the server keeps answering | stop the server on a withdrawn mark |
| T14 | The request carries no version, recipe or machine detail (the stub server records every header and the address) | add the installed version to the address |
| T15 | An update interrupted mid-download resumes, and the finished file still has to match its sha256 | skip the sha256 for a resumed file |
| T16 | Told the Mac has room for both builds, the old one answers a request during the new one's test; told it has not, the in-turn way is used | always switch in turn, whatever the memory |
| T17 | With disk to spare, two earlier builds are kept and `auster rollback` can name either; with less, the oldest is removed first and the one in use never | keep exactly one earlier build, whatever the disk |

### D7. Live steps (each on the owner's word)

- **UL1, the Studio:** install from zero; the stamp and `serving` are right; `auster status` says `current`.
- **UL2:** a test release appears; within the day's check the notification shows and `auster status`
  says what would change.
- **UL3:** two updates that change the model. One where both builds fit together (model A from 4-bit
  to 5-bit): no outage is expected, and a request is answered during the test. One where they do not
  (to model B): the outage is timed. The household's keys still work after each.
- **UL4:** `auster rollback`, to the build before and to an older kept one; no download; no re-offer.
- **UL5:** the same update with the network cut partway, then resumed.
- **UL6, the MacBook:** UL1 to UL3 on the smaller Mac. The same updates must choose differently
  there, including a build that does not fit and an earlier build removed for room.

### D10. Rollback

- **Before `release` first moves:** nothing has reached anyone. Revert on `main`.
- **A wrong release:** it gets a successor, and installed Macs are offered it within a day. As in
  1launcher's section 10, this holds only while the wrong release's own check and update still work. A
  release that breaks them is repaired by one paste of the installer line, and its notes are the only
  way to say so.
- **A wrong model:** `auster rollback` on the Mac, and a successor release that names the old build
  again or marks the new one withdrawn.
- **The check alone:** the file `off`.
- **The record:** `_update` holds no models and no conversations. Moving it to the Trash puts the Mac
  back to "no record"; the next install writes it again.

### D11. Not in this plan

- Silent updates of any kind.
- Signing of what is fetched. The sha256 in the registry is the check.
- A window, a menu-bar item, a progress bar: phase 4.
- The Apertus output filter for personal data. Its publisher has not released one yet.
- A mirror for a model whose publisher removes the file. Until there is one, a removed file means the
  installer stops with a sentence saying so, and a successor release names another build.
- MLX builds, Windows and Linux.

### D12. Facts to settle before the check

- Whether llama.cpp's numbered macOS builds are signed, and what macOS does with them when fetched by
  curl. Not downloaded yet.
- Whether a Hugging Face address that names a commit keeps working after the publisher changes or
  deletes the repository.
- Whether the chat page `llama-server` serves can take a per-person key and is usable from an iPad.
  Phase 1 tries it (BD1).
- Whether a notification sent from a launchd job shows on a Mac that has never allowed Script Editor to
  notify. 1launcher's plan has this from reports only.
- How long the Studio takes to stop a 44 GB model and answer on another. Phase 1 measures it.
- How a second build is loaded beside the first and takes over without a restart: `llama-server`'s
  router mode (its `--models-dir` and `--models-preset` options are in the installed build), or a
  second process. And what each costs in memory. Phase 1 tries it.
