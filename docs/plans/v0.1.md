room for five models is treated as one.

**Third principle (owner, 2026-11-26): Auster stands on its own.** 1launcher is where its method came
from. It is not the authority for its design. Every rule in this plan is stated here, and the plan can

## A. The recipe format and the registry

### A1. What a recipe is

A recipe is a use, such as the household assistant, and the builds that can serve it. For people it is a
folder, `recipes/<label>/`, with a README, a findings file, its system prompt and its test. For Auster it
is an id in the registry. Nothing on a Mac is found by the folder's name or the recipe's label, so both
can be renamed at any time without a migration (T36).

### A2. Ids

Every recipe, build, engine and model has a minted id, made by `tools/mint-id <kind>` from 60 random bits
(`openssl rand`), written in lowercase base32 after one letter for the kind. Patterns: recipe
`^r[a-z2-7]{12}$`, build `^b[a-z2-7]{12}$`, engine `^e[a-z2-7]{12}$`, model `^m[a-z2-7]{12}$`. An id is
never reused and never changed. The release gate fails a registry in which one id is defined twice. A
person never types an id except in the pasted line (B2), which names the recipe.

### A3. The registry

`registry.tsv` at the root of the repo, read from `release` (D3.3). Plain text: one record a line, fields
separated by tabs, at most 1,000 bytes a line and 1 MiB in all (the gate fails it above half of that).
Lines starting `#` are comments. **No field is a URL or a path** (D4): addresses are built from fixed
hosts and matched fields.

The first line is `auster-registry`, the format number and the version: `auster-registry	1	v0.1.0`.

| Record | Fields, in order |
|---|---|
| `recipe` | id, label, allowed trust tiers, people (default), context per person (minimum), context per person (maximum) |
| `engine` | id, platform, numbered build, file name, size, sha256 |
| `model` | id, Hugging Face repository, commit, file name, size, sha256, licence, trust tier, context limit of the file |
| `build` | id, recipe id, rank, engine id, model id, template, system prompt sha256, weights on the GPU (MiB), working buffers (MiB), cache per token (bytes), writing speed expected (tok/s), temperature, top-p |
| `withdraw` | build id, reason code |

| Field | Pattern |
|---|---|
| label | `^[a-z][a-z0-9-]{1,40}$` |
| trust tiers | comma-separated from `publisher` (the file is the model publisher's own), `endorsed` (a third party's build that the publisher's own page links to), `third-party` |
| people, contexts, sizes, MiB, bytes, rank, speeds | digits only, at most 15 |
| platform | `macos-arm64` (the only one in v0.1) |
| numbered build | `^b[0-9]{4,7}$` |
| engine file name | `^llama-b[0-9]{4,7}-bin-macos-arm64\.(tar\.gz|zip)$` |
| repository | `^[A-Za-z0-9._-]{1,96}/[A-Za-z0-9._-]{1,96}$` |
| commit | `^[0-9a-f]{40}$` |
| model file name | `^[A-Za-z0-9][A-Za-z0-9._-]{0,200}\.gguf$` |
| sha256 | `^[0-9a-f]{64}$` |
| licence | `^[a-z0-9.-]{2,30}$` |
| template | `gguf` (the file's own) or the sha256 of a file in `assets/` |
| temperature, top-p | `^(0|1)(\.[0-9]{1,3})?$` |
| reason code | `security`, `egress`, `quality`, `licence`, `publisher` |

- A record of a kind the Mac does not know is passed over, and so is a field after the last one it
  knows. A line that fails any pattern is passed over, and the recipe it belongs to says so (D3.3).
- **A released line is never removed or changed.** A build is withdrawn by a new `withdraw` line naming
  it. The gate holds both (D3.9).
- Rank orders a recipe's builds: the lowest rank that is appropriate on a Mac is the one it takes (D3.7).
- The figures in a `build` line are measured, on a named Mac, and recorded in the recipe's findings file
  before the line is released: weights and buffers from the engine's own report, the cache from the same,
  the writing speed from `llama-bench` at an empty context. Section C and the recipe's test use them.

### A4. Files Auster ships

`assets/` holds the files a build needs that are not the model: chat templates, system prompts and the
recipe tests. A file is named for people and found by its sha256, so renaming it changes nothing. A
template copied from llama.cpp keeps its name and is credited, with the commit it came from (MIT).

### A5. The descriptor

What `builds/<recipe id>/serving` and each `kept` entry hold (D3.1): the `build`, `engine` and `model`
lines as they were in the registry, word for word, then one line of the launch settings used: people,
context per person, address and port. Going back to a kept build needs nothing else.

### A7. The recipe's test

`assets/household-test.json`: twelve questions from phase 1's set, in the same form, graded by the same
rules as `scripts/phase-1/quiz.py`: the four safety questions, four of the format questions (one word,
three items, capitals, JSON), two sums that both builds answered, and two reading questions. It is run at temperature 0. **It passes when every safety and format
question passes, at least ten of the twelve pass, it finishes within 120 s, and the writing speed it
measures is at least 70% of the build's expected speed.** The last condition catches a model the engine
has moved partly off the GPU (`docs/phase-1.md`, step 11). Phase 2 runs it twice on each build first, to
confirm it gives the same result both times.

D3.6 step 4 also asks for "the form of a tool call". The household page sends a `tools` field with every
message, but whether either build returns a well-formed tool call has not been tried. Phase 2's first
step tries it; if neither does, the tool-call question is dropped from this recipe's test and recorded.

## B. The installer

### B1. Where things go

The data root is `~/Library/Application Support/Auster/`, owned by the person who installs and writable by
nobody else. It holds `builds/` and `store/` (D3.1), `_update/`, `engines/<sha256>/` (each engine build
unpacked, named by its archive's hash), `keys/` (mode 0700), `logs/`, `bin/auster`, the two jobs' scripts
and the installer's last run. The line in `CLAUDE.md` that names this place is written before phase 2
creates it. Nothing is written anywhere else except the two job files in `~/Library/LaunchAgents/` and, on
a yes, one line in `~/.zprofile` (B6).

### B2. The way in

One line, pasted into Terminal:

```
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/macaiport/auster/refs/heads/release/install.sh)" auster-install <recipe id>
```

The recipe is named by its id, not its label, because this line is published and can never change. `-f`
makes a missing file run nothing, and the installer is all functions with one call on its last line, so a
download cut short also runs nothing. `install.sh update` is the update (D3.6). `install.sh --check <recipe
id>` goes through every step, fetches only the small files, and changes nothing.

### B3. What the installer does, in order

Every step is skipped when it is already done, so running it again is the update.

1. **Refuse what it must:** running as root; not macOS 14 or later; not Apple Silicon.
2. **Fetch the tree of one commit** of `release` as one archive, and read its commit from the archive.
   The installer, the registry, the assets and the driver all come from it.
3. **The data root,** made and checked for ownership.
4. **The engine:** the registry's file for this platform, fetched from GitHub's release of that numbered
   build, size and sha256 checked, unpacked into `engines/<sha256>/`. Then run once: `--version` must
   name the build, and `--list-devices` gives the GPU limit (C1).
5. **The choice** (section C): the build, the number of people and the context per person, or a refusal
   that says why, in the Mac's own figures.
6. **The question:** what will be downloaded and how large, how much memory it will hold, how many
   people at what context, the address the household will use, and that it listens on the home network.
   Nothing large is fetched before the yes.
7. **The model:** the publisher asked first (D3.6 step 1); fetched from the address that names its
   commit, resumable, size then sha256 checked with `openssl`, made read-only in `store/`.
8. **The template and the system prompt** from the tree, by sha256, into `store/`.
9. **Keys, one for each device** (B7). The installer asks for the devices' names; names are labels.
10. **The jobs** (B4, B5), written and loaded.
11. **The first start:** wait for the engine, then ask the recipe's test (A7). `/health` alone is not
    taken as proof (`docs/phase-1.md`, step 11). On a fail the jobs are unloaded and the installer says
    why.
12. **The household's way in:** the address, `http://<this Mac's local name>.local:<port>`, and each
    device's key, shown as QR codes in Terminal (B7), then cleared from the screen.
13. **The records:** the stamp and `serving` (D3.1). Then exit 0.

Exit codes: 0 done; 1 stopped before anything was changed; 2 a usage error; 3 not everything was updated
(D3.6); 4 the server is down (D3.6).

### B4. The engine job

`~/Library/LaunchAgents/local.auster.engine.plist`, kept alive, runs `jobs/engine.sh` (bash 3.2). The
script:

1. reads `serving` and matches every field (D3.1);
2. while `paused` names a process that is alive, waits (D3.6 step 4);
3. checks the engine and the template against their sha256s (AD13); on a mismatch writes the reason
   into the recipe's `start` record and exits;
4. finds the home-network address: the address of the interface the default route uses. With no such
   address, it writes `no-network` into `start` and exits, and launchd tries again after its throttle;
5. `exec`s the engine with a fixed set of options that the registry cannot change: the model, `-c`
   (people × context per person), `-np` (people), `--host` that one address, `--port`, `--api-key-file`,
   `--offline`, `--no-slots`, `--cors-origins` its own two addresses (by number and by `.local` name),
   `--jinja`, the template file where the build names one, and `--ui-config-file` with the system prompt.
   The engine's own fitting is left on, as a safety net that turns "does not fit" into "slow"
   (`docs/phase-1.md`, step 11); section C's rule should mean it is never used.

The port is chosen at install: 8484 if it is free, the next free one if not, and kept in the descriptor.
If the Mac's address changes while the engine runs, the engine keeps listening on the old one. The guide
asks the household to have the router keep the Mac's address, and the check job says when it finds the
address changed (B5).

### B5. The check job

`~/Library/LaunchAgents/local.auster.check.plist`, run at load and every four hours, runs `jobs/check.sh`.
Each run, with a time limit for each part (`/usr/bin/timeout`), and its exit code ignored (D3.4):

1. `updates.sh --refresh` (D3.3).
2. **The engine probe:** one short real question with Auster's own key, which is not a household key.
   The result goes into `_update/engine`: `ok` with its writing speed, `slow` below 70% of the expected
   speed, `failed`, or `down`. The first run after a start asks a longer question, as a warm-up
   (`docs/phase-1.md`, step 10).
3. If the Mac's address has changed since the engine started, it says so in `_update/engine` and in a
   notification, and does nothing else: the check never touches the server (D2.2). `auster stop` and
   `auster start` move the engine to the new address.
4. A notification, in fixed words (D3.5), when an update waits, a build is withdrawn, or the probe found
   the engine `failed` or `down` twice in a row.

Nothing it does can stop, delay or restart the server. T18 holds it to that.

### B6. The `auster` command

`bin/auster` in the data root, a bash script. Subcommands: `status`, `update`, `rollback`, `unhold`,
`cleanup`, `verify`, `key add <name>`, `key revoke <name>`, `key show <name>`, `stop`, `start`, `remove`.
The installer asks whether to add one line to `~/.zprofile` that puts `bin/` on the `PATH`; on a no it
prints the full path to use instead. A Mac whose shell is not zsh is told the line to add.

### B7. Keys, devices and the QR code

- **One key for each device,** not each person: the chat page keeps its key in the device's browser, in
  plain text (`docs/phase-1.md`, step 3). Keys are 32 hex characters from `openssl rand`, kept in
  `keys/` with mode 0600, never printed in full and never sent anywhere.
- **Getting a key onto a device:** a QR code of the key, shown in Terminal on the Mac and cleared after.
  In phase 1 the clipboard did not reach the iPad and a QR code did (step 7). The QR code is drawn with
  macOS's own Core Image from JavaScript for Automation (`osascript -l JavaScript`), so nothing is
  installed for it. **Whether that draws a QR code an iPad's camera reads, in Terminal, is not yet
  tried;** phase 2's first step tries it, and the fallback is the image in a window, as in phase 1.
- `auster key add` and `auster key revoke` restart the engine: it reads its key file only at start
  (step 3). The restart takes 2.6 s with the model in memory.
- A QR code that signs a device in, rather than only giving it its key, waits for phase 6 (D11).

### B8. Removing Auster

`auster remove` unloads and deletes the two jobs, removes the `PATH` line it added, and lists what is left
in the data root with its size. It deletes the data root only on a second yes. Nothing else on the Mac was
touched by Auster.

### B9. After a restart (AD15)

v0.1 uses launch agents, which run in the session of the person who installed. So after a restart the
server comes back **once that person has logged in.** With FileVault on, as on the development Mac,
nobody can be logged in until the disk is unlocked. A launch daemon would start without a login, but
needs an administrator to install, and whether the engine has the GPU as a daemon is not yet known
(D12). The guide says plainly what a restart means. AD15 stays open for the owner.

### B10. What is fetched, from where

From GitHub: the installer and the tree of one commit, and the engine archive from the llama.cpp
project's release of the named build. From Hugging Face: the model file, at the address that names the
publisher's commit. Nothing else, and nothing without a yes once the question has been asked (B3 step 6).

## C. The capability rules

### C1. The figures, from one place

| Figure | Where it comes from | Test variable |
|---|---|---|
| GPU limit (MiB) | the engine's `--list-devices`, the total it gives for `MTL0` (53,084 MiB on the development Mac) | `AU_GPU_MIB` |
| Memory (bytes) | `sysctl -n hw.memsize` | `AU_RAM_BYTES` |
| Free disk (bytes) | `df -k` on the data root's volume: physically free, not counting what macOS could clear | `AU_DISK_FREE_BYTES` |

A test variable is used only when it matches `^[0-9]{1,15}$` whole. Every rule below takes its figures
from this one function and from the registry, so a test can give it any Mac.

### C2. What a build needs

For a build serving P people at a context of N tokens each:

> weights on the GPU + working buffers + cache per token × N × P

Checked against phase 1's own reports: Magistral Small at 40K for one person, 13,302 + 272 + 6,400 =
19,974 MiB (19.5 GiB; the engine reported those three exactly); Mistral Small 4 at 128K for four people
sharing it, 41,923 + 333 + 2,880 = 45,136 MiB (44.1 GiB).

### C3. Does it fit

A set of builds loaded at once fits when both hold:

1. **On the GPU:** the sum of what they need, plus 1,024 MiB, is at most the GPU limit. 1,024 MiB is the
   engine's own margin for its fitting.
2. **For the rest of the Mac:** memory minus that sum is at least 12 GiB, so that macOS and the
   household's other apps keep room. With Apertus at 32K the development Mac had 5 to 9% of its memory
   free and still worked; 12 GiB is a first value, to be measured on the 36 GB MacBook (UL6).

On the development Mac: Mistral Small 4 for four people at 32K each needs 44.1 GiB and fits, with 7.8 GiB
spare on the GPU before the margin and 19.9 GiB for the rest of the Mac. Apertus at 48K would need 55.5 GiB and does not.

### C4. Choosing the build and the context

For the recipe's number of people, take the builds in rank order and keep only the appropriate ones
(D3.7). For each, take the largest context per person between the recipe's minimum and maximum, in steps
of 1,024, that fits (C3) and that the model file allows. Use the first build with any such context. If
none has one, refuse, and say what this Mac has and what the smallest build needs. The household may
choose fewer people; the choice is made again with that number.

The development Mac gets rank 1 at 32,768 per person for four. A Mac whose GPU limit is about 27 GiB
and 36 GB of memory would get rank 2: by arithmetic, 32,768 each for two people, or 17,408 each for
four, the rule for the rest of the Mac being the one that binds. That is not measured; UL6 measures it on
the MacBook.

### C5. Side by side or in turn (D3.6 step 4)

Side by side when everything already loaded, plus the candidate for one person at 8,192, fits (C3).
In turn otherwise. Worked out at the question and again immediately before the test.

### C6. Room on disk (D3.6 steps 1, 3 and 6)

There is room when free disk, less the download, is at least the larger of 20 GiB and 5% of the volume.
When there is not, the rule names the earlier builds whose removal would make room, failed builds first,
then the oldest kept, never the one in use, and the one before it only if the person says yes. A file in
`store/` counts only when no descriptor of any recipe names it.

### C7. What C does not do in v0.1

- **It does not predict speed.** The registry carries each build's measured speed on its own Mac, and the
  recipe's test checks the speed after every start; a Mac with less memory bandwidth simply measures
  slower. A rule that refuses a build for being too slow waits for measurements on more than one Mac.
- **It does not weigh a model's quality.** The registry's order is the recipe's judgement, made from
  measurements such as phase 1's quiz.

## D. The built-in update

### D1. What is true today (read and measured 2026-11-26)

**D1.1 The requirement.** The owner, 2026-11-26: the same update process as 1launcher, built in from
the start. Starting the model checks whether a newer Auster is out, and Auster can move to newer models
"as new ones become available/appropriate".

**D1.2 Where the mechanism comes from.** This is provenance: nothing from D2 on needs it, because the
rules are stated there in full. Auster's update began from 1launcher's. Read from `docs/plans/built-in-update.md` in that repo (shipped
as its `v0.3.1` on 2026-11-25). Section numbers below are that plan's.

- An installed Mac records which version each game was set up from, in a folder `_update` (3.1).
- At most once a day, when its window opens or a game starts, the Mac fetches one text file, the
  `CHANGELOG.md` on the branch `release`, and reads the newest version heading from it. A failure counts
  as that day's try. With no network nothing is said and the game starts (2, 3.2).
- The fetch is bounded at 1 MiB, the version is taken by one fixed pattern, and nothing fetched is run.
  Every value read back from `_update` is matched whole before use (3.1, 3.2, 3.8).
- "Newer" is decided by comparing version numbers, never by "different", because GitHub may answer
  with a copy up to five minutes old (3.2).
- When a newer version is out the window shows it with what changed. One click and a yes opens Terminal,
  which fetches the installer from `release` and runs it again for every game. **The installer is the
  update:** each step is skipped when already done (1.1, 3.4).
- Nothing installs without a yes (UD1). A file named `off` stops the check. A Mac set up from a
  checkout or a named version is never offered anything and never asks (2, 3.2).
- `release` moves only to a commit that a `v` tag names, and two GitHub rulesets stop `release` and the
  tags from being rewound or deleted (3.7, UD3, UD5).
- It was added after people had installed, so each existing install needed one more paste (UD9's answer, 11).

**D1.3 Measured here** (the Studio: `/usr/bin/curl` 8.7.1, bash 3.2.57, macOS 27.2.1).

The file name's form has changed before (`.zip` in 2025, `.tar.gz` now). |
| Homebrew's `llama.cpp` 1.0.0 | Built from the tag `v1.0.0`. The arm64 bottle has its own sha256. |

| This Mac after a restart | **FileVault is on** (`fdesetup status`) and **restart after a power cut is off** (`pmset`: `autorestart 0`). As set up, nothing stored on its disk runs after a restart until someone unlocks it. |
| sha256 of a 14.3 GB file on the Studio | Ran to the end in the background. **Not timed.** Phase 1 times it (it bears on AD13). |

Measured the same day against this repo's own files: `raw.githubusercontent.com` answers with
`cache-control: max-age=300`, so an answer can be five minutes old. `--max-filesize` on a larger file
gives curl exit 56 over HTTP/2 and 63 over HTTP/1.1, and keeps nothing. Without `-f`, a missing file
is exit 0 with the code `404`. With no route the code is `000`, and the exit is 6 when the name does
not resolve and 7 when nothing answers.

**D1.4 What is different here.**

1. **The server is always on.** 1launcher checks when something is opened. A household server starts at
   boot and may then run for weeks, with nobody at the Mac.
2. **Three things change, not one:** Auster's own scripts, the engine, and the model.
3. **A model is 14 to 44 GB.** A game update re-runs quick steps; this one downloads for minutes or hours.
4. **A worse model does not announce itself.** A game that will not start is obvious. A model that
   answers a little worse is not (concept, "Quiet failure modes").
5. **Changing the model may interrupt people.** Whether two builds can be loaded at once depends on
   the Mac and on the context length. A 14 GB file took 33.4 GB in all at a 128K context, so two do
   not fit in 55.7 GB at that context, and do at a smaller one.
6. **A build may need to be taken back,** for instance when a model is reported to misbehave (concept,
   "Trust tiers"). The channel that says "newer" can also say "withdrawn".
7. **Nothing is installed anywhere yet.** No Mac needs a second paste.

### D2. Target

1. An installed Mac knows what it runs: the version of Auster's scripts, once for the Mac, and for each
   recipe the build in use, with every file of that build by sha256.
2. At most one check a day asks GitHub what `release` holds: soon after the Mac starts, and then daily.
   With no network nothing is said. **The check can never stop, delay or restart the server.**
3. **One channel.** A new engine build or a new model reaches a Mac only as a new version of Auster
   whose registry names different files. There is no second place to watch.
4. When something is waiting, the person who looks after the Mac is told in fixed words that Auster
   ships, never in words fetched from the network. `auster status` says which recipes would change, how
   large the download is, and whether this Mac can run it.
5. Nothing is downloaded or installed without a yes, and nothing that runs unattended can give one.
6. A new build is put beside the one in use. It takes its place only after it has downloaded, matched
   its size and sha256, and passed the recipe's own test in isolation. If any of those fails, the Mac
   serves what it served before. Where the Mac has the memory, the test runs while the old build keeps
   answering, and the swap costs one restart of the engine. Where it has not, the server is down for the
   length of the test.
7. Going back is one command and needs no download, for as many earlier builds as that Mac's disk
   keeps. A build someone went back from is not put back by a later update.
8. A Mac set up from a checkout or a named version is never offered anything and never asks. It is also
   never told of a withdrawal; the guide says so.
9. A build can be withdrawn by a new line in the registry, and every Mac that checks is told within a day
   of the release that
   says so.
10. The check sends nothing about the household, sends the same requests whether or not anything is
    waiting, and one file switches it off.

### D3. Design

**D3.1 The records.** Two folders in Auster's data root. Where the data root is belongs to section B;
it is a new place outside the repo and gets its line in `CLAUDE.md` first.

`builds/` is what the server runs from. `_update/` is only what the check knows. Moving `_update` to the
Trash resets the check and changes nothing the server uses.

| In `builds/` | What |
|---|---|
| `<recipe id>/serving` | the build this recipe runs: a complete descriptor (below) |
| `<recipe id>/kept/` | one descriptor for each earlier build still on disk, newest first |
| `<recipe id>/failed/` | descriptors of builds that failed their test, kept for inspection. Never served, never a rollback target |
| `<recipe id>/hold` | the build ids this recipe is not to be moved to (D3.7), one to a line |
| `<recipe id>/start` | how the engine job's last start went: `ok`, or a code such as `engine-hash`. Read by `auster status` |
| `updating` | the lock on `builds/`: a link naming the process that holds it. Taken by an update, a rollback and a cleanup |
| `paused` | present while the engine must not run, naming the update that asked (D3.6 step 4) |
| `store/<sha256>` | the files themselves: engine archives, model files, templates. Shared by every recipe, and read-only once verified |

| In `_update/` | What |
|---|---|
| `scripts` | the stamp, once for the Mac: the line followed (`release` or `checkout`), the version of Auster's scripts, the commit, the time |
| `offer` | one line: the newest version `release` held at the last check that worked, and its time |
| `tried` | one line: the time of the last try, whether it worked or not |
| `notes.md` | the changelog as last fetched |
| `noted` | one line: the version last announced, and how often (1 or 2) |
| `off` | if it exists, nothing is ever fetched. Made by hand |
| `registry` | the registry as last fetched. Read only by `auster status`. Never the source of a size or sha256 for an install (D3.6) |
| `engine` | the check job's last probe of the engine: `ok` with its writing speed, `slow`, `failed` or `down`, and whether the Mac's address has changed (B5) |
| `updates.sh` | the deployed copy of the rule file |

- **A descriptor is complete.** It is the build's registry line, word for word, with the launch settings
  that were used. Going back to a kept build uses its own descriptor, and needs neither the registry nor
  the network.
- **A build has a minted id** (section A) that is never reused. Hold, kept, failed, withdrawn and
  rollback all name a build by it. A person sees a label and a date, and picks from a numbered list.
- **The recipe id is opaque too.** Nobody outside Auster mints a number for a recipe, and
  `household-assistant` is a label that will be renamed one day. Section A therefore gives each recipe a minted id that appears in no path a person reads, and
  the folder name stays a label (`shared.md`, keys are opaque).
- **Files are counted by sha256 across recipes.** A file in `store/` is removed only when no `serving`,
  `kept` or `failed` descriptor of any recipe names it.
- **Ownership.** Before any write, the data root, `_update/`, `builds/`, every folder in them and
  `store/` must be folders that belong to the service's user and that nobody else can write to.
  Otherwise nothing is written. The engine job and the check run as that one user, who is not root
  (AD15). Nothing in section D runs as root.
- **Reading.** Every value read back is matched whole before use, a file that is a link or too large is
  treated as absent, and nothing is ever run. The one-line records (`scripts`, `offer`, `tried`,
  `noted`) are read as a single line of at most 4,096 bytes with a fixed number of tab-separated fields;
  a second line, or a field too many, makes the record absent.
  Descriptors, `hold` and the registry get readers of their own, each with a stated bound and one
  pattern per field. `hold` is one build id to a line, at most 64 lines. **A `hold` that cannot be read
  passes its recipe over; it is never treated as empty.**

**D3.2 The rule file.** `common/updates.sh` holds the rules for what is installed and what is on offer.
Every caller uses it, and each install puts a copy in `_update`. It begins as a copy of 1launcher's file
at `b056bf3`, credited in its header, and is Auster's own from then on (AD12). Its rules:

- **The word for the Mac,** the first that applies: `off`, if the file `off` exists; `none`, if there is
  no stamp; `manual`, if the stamp's line is not `release`; `unknown`, if there is no `offer`; `ready`
  (D3.3); `current` otherwise. `manual` is for the whole Mac: a checkout is never offered anything.
- **Once a day.** `tried` holds the time of the last try. A try made less than a day after it fetches
  nothing. `tried` is written before the fetch, so a failure uses up the day (D3.4 has the one exception).
- **The bounded fetch.** `/usr/bin/curl` with the person's own curl settings ignored, HTTPS only, a
  ten-second limit and a cap of 1 MiB, the body to a file. The answer is taken only when curl's exit is
  0, the code is 200, the file is within the cap when measured again, and a version is found in it.
- **Newer, never different.** A version is three numbers compared as numbers, read from the first
  changelog heading of the form `## v<a>.<b>.<c> (`. An answer that names an older version than `offer`
  holds never lowers it, because an answer can be five minutes old.
- **The notes cleaner.** Before any fetched note is shown: headings lose their marks, paragraphs are
  joined, emphasis marks and every control character are removed, and the text stops at 200 lines or
  12,000 bytes with a pointer to the changelog.
- **A contract between versions on one Mac.** Its options and its output lines are used by callers built
  by other versions. A later version may add an option or a field at the end of a line, and never
  changes or removes one.
- **Its test variables:** the folder, a time that stands for now, and the two programs a test replaces
  (`AU_UPDATE_DIR`, `AU_UPDATE_NOW`, `AU_CURL`, `AU_OPEN`).

What Auster's file does that the one it began from does not: one stamp for the Mac in place of one per
game; the readers of D3.1; the second fetch, the joint write and the recipe lines of D3.3; the no-route
rule of D3.4; the ownership rule over `builds/` and `store/`; the call to section C's rule; and a
cleaner that also removes the two-byte control characters.

**D3.3 What a check fetches, and what it concludes.** Two small text files from `release`, **both on
every check**, each bounded at 1 MiB, each read by fixed patterns, neither run:

1. `CHANGELOG.md`: the newest version and what changed.
2. The registry (section A): every recipe's builds.

Fetching both every time means a second request never marks a Mac as behind.

- The registry's first line is its format number and its version. A Mac uses a registry only when that
  version equals the newest in the changelog just fetched: each file can be up to five minutes stale on
  its own (D1.3). `offer`, `notes.md` and `registry` are replaced together, and only when both files
  were read and their versions agree. Otherwise none of the three is written, the check counts as a
  failed try, and nothing is said.
- A registry line with a format number the Mac does not know, or with any field that fails its pattern,
  is passed over. Extra fields it does not know are ignored. A Mac that can read no line for a recipe
  shows that recipe as `passed over (cannot be read)` in `auster status` and sends no notification.
- The word for the whole Mac is one of the six of D3.2.
  `ready` means: the offered version is newer than the scripts version, **or some recipe has a build
  waiting.**
- Each recipe also gets one line: `same`; `waiting` (the build D3.7 picks for it is not the one it
  serves); `passed over`, with the reason (does not fit, no room, held, cannot be read); or `withdrawn`
  (the build it serves is marked).
- A person who says no to a build leaves it `waiting`. `auster status` keeps showing it and
  `auster update` offers it again. The notification is not repeated (D3.5).
- A notification is sent for a new version. A build that starts `waiting` for a reason on the Mac
  itself, such as memory freed, shows in `auster status` only.

**D3.4 When the check runs: two jobs, so that the check cannot hurt the server.**

- **The engine job** keeps the engine running. It starts what `serving` names and nothing else. It does
  not read `_update`, does not call `updates.sh` and fetches nothing. Before each start it checks the
  engine and the template against the sha256s `serving` gives (AD13). On a mismatch it does not start,
  and writes the reason into the recipe's `start` record. While `paused` names a process that is still
  alive, it waits.
- **The check job** runs `updates.sh --refresh` soon after it is loaded and then every few hours, and
  asks the engine one real question (B5). The
  rule file's `tried` stamp keeps that to one check a day. The call has a time limit and its exit code is
  ignored. When `updates.sh` is missing, unreadable or failing, the check job does nothing.
- A try that never reached GitHub, because the Mac had no route yet, does not use up the day: the next
  firing tries again. "No route" means curl's exit code 6 or 7 on the first request. `tried` is written
  before the fetch, and put back to what it was only on those two codes. Every other
  failure uses up the day, a check stopped by its time limit included.
- **Why two.** launchd does not fire a timed trigger for a job it is already keeping alive (`man
  launchd.plist`). One job would therefore need a hand-written wrapper that supervises the engine and
  also sleeps for a day, and a fault in that wrapper or in the check would take the household's server
  down. Two plain jobs are fewer moving parts than that wrapper.
- A check that runs with nobody at the Mac is acceptable here because Auster is a background service
  already, and because the check can only read and record (T19).
- Whether the two jobs are launchd agents or daemons, and what that means on a Mac with FileVault, is
  decision AD15.

**D3.5 How the person is told.** v0.1 has no window. So:

- **A notification carries one fixed sentence that Auster ships.** It may include a version and a recipe
  label, each matched against its pattern first, and each passed to `osascript` as an argument, never
  built into AppleScript source. No text from the changelog or the registry is ever put in a
  notification. At most two per version.
- **`auster status`** prints the word for the Mac, each recipe's line, what would change and how large
  the download is. It also says when checks are switched off and since when, which builds are held, and
  when a build in use is withdrawn, and how each engine job's last start went. Text from fetched notes
  appears only through the notes cleaner: control characters removed, length capped.
- A notification needs someone logged in at the Mac. If AD15 lands on a daemon there are none in v0.1,
  and `auster status` is the only channel.
- Either way, a Mac that nobody sits at tells nobody, and that includes a withdrawal. The gap is
  accepted for v0.1 and said in the guide. From phase 4 the launcher window and the menu bar fill it.

**D3.6 The update itself.** `auster update`, run at the Mac's own screen, writes a `.command` file and
hands it to Terminal, so that the person sees every line. The file is made in a new folder that only the
person can read, holds constants only, and removes itself and its folder when it ends. Run over SSH, the
update runs in that session instead, so the questions are asked where the person is. Either way it
fetches `install.sh` from `release` into a file, never into a pipe, and runs it only on a 200. `install.sh`
fetches the tree of one commit and runs the driver inside it. So the installer, the driver and the
registry all come from one commit, and the code that drives an update is always the newest.

The driver holds the `updating` lock. A second update, a rollback or a cleanup that finds a live lock
refuses. A lock whose process is gone is taken over.

**Every size and sha256 used below comes from the registry inside the fetched tree**, never from the
copy in `_update`.

For a recipe whose appropriate build is the one it serves, the steps print `OK` and nothing is fetched.
For one whose appropriate build is held, one line says so and nothing changes. For one with a different
build:

1. **Before anything is fetched.** The capability rule (section C) must say the new build fits, counting
   everything that would be loaded at the same time. The disk rule must say there is room: as things
   are, or after removing earlier builds it names. And, unless `store/` already holds the file, the
   publisher is asked about it with a `HEAD` request: a size or hash it reports that differs from the registry's stops the recipe, and so
   does a 404 ("the publisher no longer offers this file"). On any of these the recipe is passed over
   with one sentence, the other recipes go on, and the update ends with exit code 3 ("not everything was
   updated").
2. **The question.** What will change; the download size; which earlier builds would be removed, and
   that they stay removed if the download then fails; which way the switch will go on this Mac, and for
   how long the server will not answer. Nothing has been fetched yet. A no leaves everything as it was
   and the build stays `waiting`.
3. **The download.** Skipped when `store/` already holds a file with that sha256. Otherwise the file is
   fetched from the address that names the publisher's commit, with no login and with the person's own
   curl settings ignored. A resume asks that same address again, never a saved address of the CDN, which
   expires. The size is compared, then the sha256. A mismatch deletes the download and stops this
   recipe. Room is worked out again before the download starts. Earlier builds are removed only at the
   moment the room is needed. The build before the one in use goes only if the question named it and
   the person said yes. A Mac whose disk cannot hold the build in use and the download together is
   passed over, with that reason.
4. **The test, in isolation.** The update itself starts the candidate, not the engine job: on
   `127.0.0.1` only, on a free port, with a key made for the test and deleted after it. No household key
   reaches it, and nothing on the network can. The recipe's test asks fixed questions and checks the
   form of the answers, including the form of a tool call. **A tool call is never run.**
   - **Side by side,** when section C says everything loaded plus the candidate fits with its margin:
     the engine job keeps serving during the test.
   - **In turn,** when it does not: the update writes `paused`, naming its own process, and stops the
     engine. launchd starts the engine job again, and the job waits for as long as that process is
     alive. So an update that is killed, or a Mac that loses power, ends the wait by itself.

   Fit is worked out again immediately before the test. If the way has changed from what the question
   said, the recipe stops with exit code 3. It never changes way silently.
5. **The switch.** The candidate is stopped, whether it passed or failed. On a pass the old descriptor
   is copied into `kept` first, and then `serving` is replaced in one rename. On a fail the candidate's
   descriptor goes to `failed` and `serving` is untouched. Then the engine runs again: in turn, by
   removing `paused`; side by side after a pass, by stopping the engine once, so that launchd starts the
   job on the new `serving`. Then the update
   asks the server for one answer. **If the server does not answer, the update says plainly that the
   server is down and how to start it, and exits with code 4.**
   - `serving` is rewritten only after a pass, and at every start the engine job serves what `serving`
     names. So a power cut at any point brings back the last build that passed.
   - A lock left by an update that died is reported by `auster status`. Unfinished downloads are
     counted by the disk rule and removed by `auster cleanup`.
   - Side by side, the old engine may have been killed for memory during the test. The update checks
     that it is alive before it says anything succeeded.
   - **The takeover is a restart.** v0.1 has no front door, and `llama-server`'s router mode needs the
     model's name on every request, so one build cannot take over from another without a restart. The
     gap is the time the engine takes to start on files already tested; phase 1 measures it. A switch
     with no gap waits for phase 6's front door.
6. **Earlier builds stay on disk for as long as the disk rule allows.** Section C sets how much free
   space this Mac must keep. Above that, every earlier build stays. Below it, failed builds go first,
   then the oldest kept build, and never the one in use. `auster cleanup` lists what it would remove,
   asks, and removes nothing on a no.

`auster rollback <recipe>` lists the kept builds, with any that are withdrawn marked, and goes back to
the one chosen. Before it switches, it checks the size and sha256 of the engine, the model and the
template again. It refuses a failed build. It refuses a withdrawn build unless told `--withdrawn-ok`, and
then prints why the build was withdrawn. It uses the kept descriptor's own settings and switches by
steps 4 and 5. Only when its own test has passed does it write the build left behind into `hold`. Going
back onto a build that is itself held takes that build off the list. `auster unhold <recipe>` clears a
recipe's holds.

`auster verify` checks every file that `serving` names against its sha256 (AD13).

Where a Mac has room to keep several models loaded at once, which ones it keeps loaded is a rule of
section C, not of the update.

**D3.7 "Available and appropriate".** A build is available when the registry in the fetched tree lists
it. It is appropriate for a recipe on a Mac when the recipe allows its trust tier, the capability rule
says it fits, it is not withdrawn, and it is not in that recipe's `hold`. All four are decided on the
Mac. The installer never moves a recipe to a build that is not appropriate.

**Which build a recipe takes.** Section A gives each recipe's builds an order. Of the appropriate ones,
a recipe takes the first. `waiting` means that build is not the one it serves. A build that comes after
the one served is never offered, unless the one served has been withdrawn; it is otherwise reached only
by `auster rollback`. Without this rule every Mac would be `ready` for ever, since a released line is
never removed (D3.8).

**D3.8 Withdrawn builds.**

- A build is withdrawn by a `withdraw` line in the registry that names it (A3), with a reason **code** from
  a fixed list: `security`,
  `egress`, `quality`, `licence`, `publisher`. The words shown for a code are Auster's own, from the code
  on the Mac. A code that is not in the list shows as "withdrawn" and nothing more.
- A build is withdrawn only by a release whose version rises. A registry line that has been released is
  never removed or changed; a withdrawal is a new line. The release gate holds both (D3.9).
- A Mac serving a withdrawn build says so at the next check, with a notification in fixed words, and in
  `auster status`, until it serves something else. It keeps serving. Auster never stops a household's
  server from a distance (AD9).
- A withdrawn build is never offered, and a rollback to one is refused without the flag (D3.6).
- A Mac whose state is `off` or `manual` is not told. The guide says so.
- The registry never loses a line and is not read above 1 MiB, so it has a ceiling. Section A sizes a
  line so that the ceiling is far off, and the gate fails a registry over half of it.

**D3.9 Releases and published names.** `release` moves only to a commit a `v` tag
names; the changelog's version headings have one fixed form, which a gate checks before a tag is made;
no tag is ever named `release`. Each change in the changelog opens with one bold sentence saying what a
household will notice. The gate here asks three more questions:

- the registry's version line equals the tag;
- no line that `origin/release` holds is missing or changed;
- every line that is not withdrawn answers a `HEAD` at its publisher with the registry's size and hash.

Before each move of `release`, the tagged commit is taken by `install.sh update` on one Mac, through the
test variables. After each move, one installed Mac is looked at within the day. The first release after
v0.1 changes no engine and no model, so the first real offer risks only the mechanism (AD14).

Once anyone has installed, these can never move: the address of `CHANGELOG.md` and of the registry on
`release`, the word `update` after `install.sh`, the form of a registry line (which is why it carries a
format number from the first release), and the form of a recipe id and of a build id.

The repo has been public since 2026-11-26, and a file on `main` reads without a login. There is no
`release` branch yet, so the two files the check reads answer 404 until the first release. The tests
never use the network: they run against a stub curl that answers by address (the rule file's `AU_CURL`),
including `HEAD`, a range and the redirect.

**D3.10 Trust, and what this sends.**

- **What runs.** An update runs code from `release`. Whoever can move `release` reaches every installed
  Mac within a day, one yes away from running their code. It is the largest risk in this plan.
- **What stands against it.** The first yes: the one given before the fetched installer runs. The
  questions asked later are asked by the fetched code itself, so they do not protect against a bad
  release. The rulesets stop `release` being rewound or deleted and a `v` tag being moved. They do not
  stop `release` being moved forward to any commit, or a new tag being made: "only tagged commits" is the
  owner's own gate, which an intruder skips. None of this stops whoever holds an owner's credential: the
  owner, any session on the owner's Macs that can push, a token GitHub holds for the repo, or GitHub
  itself.
- **Model and engine files are not trusted by where they come from.** Each is named in the registry by
  size and sha256. Hugging Face and its CDN carry the bytes and cannot change what a Mac accepts. GitHub
  can: it serves the registry those hashes come from.
- **A hash shows that a file is the one that was chosen, not that it is safe.** Safety rests on the
  short list of models, the trust tiers, and the isolation of D3.6 step 4.
- **What is sent.** Two requests to GitHub on each check, the same two whether or not anything is
  waiting. Each names curl and its version, and nothing of Auster's. GitHub sees the Mac's network
  address and the time, which is shortly after the Mac starts or one of the check job's daily times. A
  download is seen by Hugging Face and by the CDN it redirects to: the address, the file and the time,
  with no login.
- **Who is never asked.** A Mac whose state is `off`, `none` or `manual`.

### D4. What section D needs from A, B and C

Sections A to C answer each item below. What they leave open is in D12.

- **From A:**
  - The form of a recipe id and of a build id, each as a pattern. Both minted, neither reused.
  - The registry: its first line (format number, version), and the form of a build's line. No field is a
    URL or a path. Each field has a pattern, and addresses are built from fixed hosts and matched fields:
    the model's repository, commit and file name; the engine's numbered build and file name; sizes;
    sha256s. An engine build is named by its build number and file name, never by a version such as
    "1.0.0", and never by a name worked out from a pattern (D1.3).
  - What the capability rule needs to know about a build: its size, its context length, and what it
    costs in memory per person.
  - A label for people, with its pattern; the trust tier; the withdrawn mark and its reason code.
  - The recipe's test: how it is run, its time limit, what counts as a pass, and that it gives the same
    result twice.
- **From B:**
  - The data root. Where `auster` lives and how it reaches the person's `PATH`.
  - An installer whose every step is skipped when already done, so that running it again is the update;
    that honours `hold`; and that asks the question of D3.6 step 2 itself. `install.sh update`, and the
    driver for every recipe set up on the Mac. A dry run.
  - Exit codes: 0, 3 (not everything was updated) and 4 (the server is down) are fixed here; B fixes the
    rest, and the sentences a person reads.
  - The two launchd jobs, their user, and decision AD15.
- **From C:** rules evaluated on the Mac, never constants. Does this set of builds fit together, loaded
  at once, at the working context and with people using it. How much disk must stay free on this Mac,
  and which earlier builds may be removed to make room. Each answers with a reason a person can read.
  Each takes its figures for memory and disk from one place, which a test can replace.

### D10. Rollback

- **Before `release` first moves:** nothing has reached anyone. Revert on `main`.
- **A wrong release:** it gets a successor, and installed Macs are offered it within a day. `auster
  update` always fetches the newest installer, so a release whose installer is wrong is repaired by the
  next one.
- **What a successor cannot repair:** the deployed `updates.sh`, the check job and the writer of the
  `.command` file. A release that breaks one of those leaves the Macs that took it silent, repaired only
  by one paste of the installer line. That is this plan's blast radius. It is why the check cannot
  affect the server (D3.4, T18), and why each release is run on one Mac before `release` moves and
  looked at after (D3.9).
- **A wrong model:** `auster rollback` on the Mac, which holds it there; and a successor release that
  marks the build withdrawn.
- **Going back to an older Auster:** by pasting the installer line with a tag. The state becomes
  `manual` and nothing is offered until the plain line is pasted again. An older version passes over
  records it cannot read; it never trusts them.
- **The check alone:** the file `off`.
- **The check's records:** `_update` holds nothing the server uses. Moving it to the Trash puts the
  check back to "no record"; the next install writes it again. `builds/` is not like that: it is what
  the server runs from.

### D11. Not in this plan

- Silent updates of any kind.
- Signing of what is fetched. The sha256 in the registry is the check. Requiring signed tags on
  `release` is worth its own look.
- A window, a menu-bar item, a progress bar: phase 4.
- A switch with no gap, a household's own switch to stop on a withdrawal, and a QR that signs a device
  in rather than only giving it its key (`docs/phase-1.md`, step 7): all wait for phase 6's front door.
- Staging. Every Mac is offered the same version within a day. Exposure is limited by the yes, by AD14,
  and by how fast a release is replaced or a build withdrawn.
- Any report from a Mac to the maintainer. A model that answers worse is learned of only from an issue
  someone chooses to open; `auster rollback` prints where.
- The Apertus output filter for personal data. Its publisher has not released one yet.
- A mirror for a model whose publisher removes the file. A removed file means the recipe is passed over
  with a sentence, and a successor release names another build. Earlier builds kept on disk are the
  only copy a Mac has.
- MLX builds, Windows and Linux.
